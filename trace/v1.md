## 1. What AgTR is

An **AgTR** (Anchored Agent-Trace Receipt) is a signed, machine-verifiable record that an **autonomous agent run executed a named sequence of pipeline stages**, producing a committed execution trace — anchored into a daily Merkle root and independently verifiable without trusting the issuer.

AgTR answers:

1. **What ran** — the named pipeline stages, in execution order, each with its duration and status.
2. **When** — the run start timestamp and total elapsed time.
3. **Which run** — a salted commit over the run's idempotency key (`request_id_commit`), joining this trace to the same run's AActR (authority) and AQR (quality) receipts.
4. **What the full trace contained** — a salted commit (`trace_commit`) over the complete detailed trace, which may carry PII or client data and therefore never appears in the signed body in plaintext.

**Load-bearing honest claim.** AgTR proves **execution PROVENANCE, not behavior correctness**. It certifies that a run with the recorded stage structure, timings, and outcome occurred at time T, signed by issuer I — not that the agent behaved correctly, that the trace is complete, or that any action it took was authorized or wise. The verifier records the issuer's asserted execution path; it does **not** re-execute, re-time, or judge the run.

Positioning phrase: **verifiable execution provenance, not verified behavior.**

### 1.1 Demarcation from neighbouring families

| Family | Answers |
|---|---|
| AActR (`ar.action.v1`) | "An agent **acted** — executed verb V against target D — on the workspace's behalf." |
| AQR (`ar.quality.v1`) | "An agent **evaluated** output Q and reached quality verdict Y." |
| AGR (`ar.guard.v1`) | "An agent **screened** input I and reached a safety verdict." |
| **AgTR (`ar.trace.v1`)** | **"An agent *ran* — executing these named pipeline stages in this order — and this is the execution path."** |

AgTR is the execution-provenance leg of the verifiable-agent receipt quartet. AActR records *what authority was consumed*; AQR records *whether the output met a quality bar*; AGR records *whether the input was safe*; AgTR records *how the run executed, stage by stage*. These are four distinct questions; AgTR is not a superset or replacement for the others.

## 2. Wire format

An AgTR is an **`ar.trace.v1` Claim** in the shared **v=2 envelope** (`@dekimuhq/anchors-envelope`): Ed25519-signed, RFC 8785 (JCS) canonical JSON, `claim_type`-discriminated. AgTR adds **no cryptographic primitive** — it reuses the envelope core verbatim. See [`envelope/`](../envelope/) for the shared wire mechanics; this document specifies only what AgTR constrains or adds.

### 2.1 Envelope constraints (AgTR-specific)

| Field | Constraint |
|---|---|
| `claim_type` | MUST be the exact string `"ar.trace.v1"`. |
| `subject` | MUST be `null` (§4). AgTR is run-level; the run target lives in the body as `request_id_commit`, never as the envelope subject. |
| `kind` | `decision` (default v1.2 issuers SHOULD emit). |
| `tsa` | OPTIONAL. Trusted timestamp is opt-in (FAMILY-CONSISTENCY §2). |
| `credentialStatus` | Absent. AgTR is a **Status-List non-consumer**: a trace is a point-in-time fact about an execution that occurred; there is no suspension/revocation surface in v1 (FAMILY-CONSISTENCY §4). |
| `prev` | OPTIONAL. MAY chain the trace receipt to the same run's AActR or AQR receipt as additive bookkeeping; not required for validity. |
| `policy_uri` / `policy_hash` / `policy_version` | Envelope-level policy block identifying the tracer/pipeline configuration under which the run executed. All three are OPTIONAL unvalidated passthrough. |

### 2.2 Leaf identity

`claimId = "ar.trace.v1:" + envelope.id`. This claimId — not the bare `envelope.id` — is the single leaf preimage across the inline anchor, the audit-log key, and the daily Merkle root (`tree_head_root = "sha256:" + RFC6962-leafHash(claimId)`).

## 3. Body — `AgTRBody`

```jsonc
{
  "profile": "agent.trace",                     // v1 ships one profile (§5)

  // Run identity — committed, joins to the same run's AActR/AQR.
  "request_id_commit": "sha256:<hex>",           // commit(salt, canonicalize(requestId)) — run idempotency key

  // Capability (OPTIONAL). Plaintext verb, non-PII.
  "capability": "operator.draft-reminder",       // e.g. <ns>.<op>; absent for policy-authorized runs

  // Execution skeleton — plaintext, ordered as executed.
  "stages": [
    { "stage": "validate", "ms": 12, "status": "ok"    },
    { "stage": "oversight","ms": 34, "status": "ok"    },
    { "stage": "execute",  "ms": 98, "status": "ok"    }
  ],

  // Terminal outcome.
  "outcome": "ok",                               // "ok" | "error" | "denied" | "checkpoint"
  "error_stage": "execute",                      // REQUIRED iff outcome === "error"

  // Full trace — committed (may carry PII / client data).
  "trace_commit": "sha256:<hex>",                // commit(salt, canonicalize(fullDetailedTrace))

  // Timing.
  "started_at": "2026-06-20T10:00:00.000Z",     // RFC 3339 / ISO 8601 UTC
  "total_ms": 144,                               // non-negative integer

  // Policy provenance (OPTIONAL passthrough).
  "policy_uri": "https://...",
  "policy_hash": "sha256:<hex>",
  "policy_version": "1.0",

  // Mandate binding (OPTIONAL, additive — §4.4).
  "credential_id": "<claimId>",                  // authorizing mandate's credential id
  "caveats_consumed": {                          // present iff credential_id is present
    "data_scope": "ws_abc123",
    "spend_step": 1,
    "spend_currency": "actions",                 // OPTIONAL
    "capability": "operator.draft-reminder"
  }
}
```

`field_root` (a `sha256:<hex>` selective-disclosure root over the committed fields) is added **issuer-side at mint** and appears in the receipt body; it is not part of the canonical body *input*.

### 3.1 Field rules

- **Plaintext fields** (`profile`, `capability`, `stages[*].stage`, `stages[*].ms`, `stages[*].status`, `outcome`, `error_stage`, `started_at`, `total_ms`) are legible by design — an execution-provenance receipt is useless if an operator cannot read *how* the machine ran. Stage labels are fixed pipeline identifiers (`validate`, `oversight`, `execute`, `meter`, …) that describe the machinery, not the data. None is PII.
- **`request_id_commit`** is a salted `sha256` commit, `commit(salt, canonicalize(requestId))`, over the run's idempotency key. It **joins** this AgTR to the same run's AActR (`ar.action.v1`, which already carries `request_id_commit`) and any AQR for the same output — one run, one `requestId`, one family of correlated receipts.
- **`trace_commit`** is a salted `sha256` commit over the **full detailed trace** (stage inputs, outputs, errors, and any other detail recorded by the tracer). Because the detailed trace may carry PII or client data, committing keeps the publicly-anchored, immutable receipt GDPR-clean while still binding the exact execution record. Salts live in the issuer's owner-revealable reveal map, never in the signed envelope.
- **`outcome: "error"`** also mints: "the run failed at this stage" is as audit-worthy as a success. `error_stage` MUST be present and non-empty when `outcome === "error"`.
- **`outcome: "checkpoint"`** records a run that paused for human approval — execution provenance of the checkpoint event itself.
- **`outcome: "denied"`** records a run that was refused (e.g. by an oversight gate) — the pipeline ran, reached the denial, and stopped.

### 3.2 Commit discipline

Every commit is `sha256(salt ‖ value_utf8)` over a single canonicalized value. A field binding multiple values MUST canonicalize them into one JSON object first (`commit(salt, canonicalize({...}))`) — never `H(a ‖ b)` over variable-length operands.

### 3.3 Plaintext stages are not a PII leak

Stage labels are fixed pipeline identifiers that describe the *machinery*, not the data. Anything data-bearing (stage inputs, outputs, error messages, LLM prompts/completions) lives in the full detailed trace behind `trace_commit`, never in the signed body. This is the same PII-clean split as AActR (plaintext `verb`/`rule_id` + salted `decision`/`params` commits) and AQR.

## 4. Subject — null (run-level)

`subject` is `null` on every AgTR. The run's identity is `request_id_commit`; the run's target lives in the body as committed fields, never as the envelope subject. If a future profile genuinely targets a named data subject, that is a `v2` per-event split, not a v1 change.

### 4.4 Mandate binding (OPTIONAL, additive)

When the run executed under a scoped agent credential (the gated capability door), the receipt MAY bind the authority it exercised:

- **`credential_id`** — the authorizing mandate's credential id (the gateway `AgentCredentialEnvelope.credentialId`, equal to the ADR grant `claimId`). Plaintext and revocation-checkable. **Absent** for policy-authorized runs (a run under an automation rule the owner enabled has no per-run mandate).
- **`caveats_consumed`** — the attenuated authority this run consumed: `data_scope` (the bound exercised, a non-PII selector), `spend_step` (budget units decremented), `spend_currency` (OPTIONAL label for the budget dimension), `capability` (the verb invoked). These are plaintext, non-PII *bounds* — never the data itself; any PII target stays in `trace_commit`.

`AgTRCaveatsConsumed` is defined **locally** in `@dekimuhq/trace-profiles` and has the same shape as AActR's `AActRCaveatsConsumed`. The two are kept independent — families do not cross-import types.

**Binding integrity rules** (enforced by the reference verifier, §6):
- An empty `credential_id` is rejected (`credential_id.invalid`).
- Malformed `caveats_consumed` is rejected (`caveats_consumed.invalid`).
- `caveats_consumed` present without `credential_id` is rejected (`caveats_consumed.orphan`) — caveats are meaningless without the credential they bound.

Both fields are additive: receipts minted before this addition verify byte-equal, and policy-authorized runs simply omit them (keys absent, never `null`/`undefined`).

**What mandate binding does and does NOT prove.** `credential_id` and `caveats_consumed` are **issuer-asserted descriptive metadata**. The capability chain itself lives, signed, in the mandate token. A stateless single-receipt verifier — including `verify.dekimu.com` — sees only the receipt body and **cannot re-derive or cross-check** that the recorded mandate actually granted the claimed scope; it can only confirm the body is internally consistent (the integrity rules above). `valid: true` is never proof that a run was authorized (§6).

## 5. Profiles (v1)

One profile: **`agent.trace`** — the Hub capability pipeline is the only v1 issuer. The profile validator (`validateAgentTrace` in `@dekimuhq/trace-profiles`) is an **advisory secondary surface** that asserts:

- `profile` === `"agent.trace"`.
- `request_id_commit` matches `sha256:<64hex>`.
- `stages` is a non-empty array; each element has a non-empty `stage` string, a non-negative integer `ms`, and `status ∈ {ok, error, skipped}`.
- `outcome ∈ {ok, error, denied, checkpoint}`.
- `error_stage` is present and non-empty when `outcome === "error"`.
- `trace_commit` matches `sha256:<64hex>`.
- `started_at` matches RFC 3339 format and is `Date.parse`-able.
- `total_ms` is a non-negative integer.
- `policy_hash` (when present) matches `sha256:<64hex>`.
- `credential_id` (when present) is a non-empty string.
- `caveats_consumed` (when present) is only valid with `credential_id`.

**Authoritative vs advisory (matches AActR/AQR convention):** the central `verifyTraceBody` (the family `body_schema`) is the **authoritative** gate — it validates the full body and is what the envelope signature binds. The per-profile validator is advisory and may use a distinct error-code namespace (prefix `trace.*`). Where a validation rule appears in both (e.g. `started_at` RFC 3339), it MUST be identical — the two validators never disagree on the central verdict. A `body_schema` pass is what matters for receipt validity; a profile-validator pass is supplementary.

Profile extensibility follows the family factory — a second profile would ship as `defineFamily({ profiles: { "agent.trace": …, "agent.trace.v2": … } })`, not as a breaking change to the wire format.

## 6. Verification surface

- **Anchor log:** `https://verify.dekimu.com/trace/v1` — RFC 9162 inclusion against the signed daily root.
- **Receipt verification:** signature + canonicalization + inclusion + body-shape + (when present) mandate-binding integrity.
- **Owner reveal:** the owner re-reveals `requestId` via the issuer's reveal map, re-derives `request_id_commit`, and confirms the receipt binds the run shown in their run-log. The owner may separately re-reveal the full detailed trace to re-derive `trace_commit` and confirm the trace was not altered after signing.
- **Cross-family join:** `request_id_commit` joins this AgTR to the same run's AActR (`ar.action.v1`) and any AQR (`ar.quality.v1`) — a verifier may confirm all three carry the same commit for the same run.

**What a single receipt does NOT prove.** A stateless single-receipt verifier confirms the receipt is well-formed and that the `credential_id` / `caveats_consumed` fields (when present) are *internally consistent*. It CANNOT:
- Re-execute the run or confirm stages actually occurred as recorded.
- Confirm `total_ms` equals the sum of stage `ms` values (clocks, gaps, and parallelism make this not generally true — the issuer asserts both; a consumer may compare).
- Confirm `outcome` agrees with the last stage's `status` (not enforced — the verifier records, it does not re-derive).
- Confirm the referenced mandate exists, is unrevoked, or actually granted the claimed scope — those are issuer-asserted and stateful, checkable only by the issuing/consuming gateway.
- Confirm the detailed trace behind `trace_commit` is complete, correct, or safe.

`valid: true` means: "this receipt is well-formed, the signature is valid, and (if checked) it appears in the daily anchor log." It is not proof that the run behaved correctly.

---

## 7. Versioning

`ar.trace.v1` is frozen on public flip. New fields are additive and OPTIONAL with graceful degradation; breaking changes require a `v2` discriminator. A profile that targets a named data subject (changing the null-subject rule), or per-stage selective disclosure, are the canonical examples of `v2` splits.

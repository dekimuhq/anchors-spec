## 1. What APIIR is

An **APIIR** (Anchored PII-Redaction Receipt) is a signed, machine-verifiable record that **a PII-redaction pass ran over content before that content was sent to a language model** — anchored into a daily Merkle root and independently verifiable without trusting the issuer.

APIIR answers:

1. **Which redactor ran** — the provenance string of the exact redaction engine, pinned by its golden-hashed rule corpus (`ruleset_hash`).
2. **What it found** — per-category removal counts (EMAIL, IBAN, VAT, PHONE, CARD, CLIENT).
3. **Over what input and toward what output** — `input_commit` and `output_commit` are dual salted commits binding the original content and the sanitized prompt that actually reached the model, without ever exposing the content itself in the anchored record.

### 1.1 Honest claim (load-bearing)

An APIIR receipt certifies **provenance of a redaction pass, NOT a guarantee that the content is PII-free**.

The precise, locked claim is:

> *Redactor R (pinned by `ruleset_hash`) ran over content committed as `input_commit`, removed the category counts recorded in `counts`, and produced sanitized content committed as `output_commit`, at time T, signed by issuer I.*

The detector is regex + Luhn-gated. It **misses** free-text names, postal addresses, dates of birth, national IDs outside the VAT shape, and novel formats. Therefore:

- The verifier validates body shape only. It **never** re-scans the original content for missed PII and **never** asserts completeness.
- The phrases "PII removed", "safe", and "anonymized" MUST NOT appear in copy, field names, or the verify renderer. The only sound claim is the provenance framing above.
- `ruleset_hash` is the reproducibility anchor: it golden-pins the exact detector rule corpus and version so a reader sees precisely which rules ran.

### 1.2 Demarcation from neighbouring families

| Family | Answers |
|---|---|
| ATokR (`ar.tokenization.v1`) | "Values were swapped for **reversible vault tokens** (crypto-shred; vault-held)." |
| `ar.anonymization.v1` | "Data was **irreversibly** anonymized — re-identification is not possible." |
| `ar.lineage.v1` | "This data-flow **provenance graph** traces where data came from." |
| **APIIR (`ar.redaction.v1`)** | **"Redactor R ran over this content before model send — these categories and counts were removed, and the sanitized prompt is committed as `output_commit`."** |

Redaction is **reversible** (the controller holds the map; nothing irreversible happened) and **point-transform** (a single before/after, not a graph). It is distinct from tokenization (no vault, no crypto-shred, substitution in-process) and from anonymization (reversible, not an identity guarantee).

## 2. Wire format

An APIIR is an **`ar.redaction.v1` Claim** in the shared **v=2 envelope** (`@dekimuhq/anchors-envelope`): Ed25519-signed, RFC 8785 (JCS) canonical JSON, `claim_type`-discriminated. APIIR adds **no cryptographic primitive** — it reuses the envelope core verbatim. See [`envelope/`](../envelope/) for the shared wire mechanics; this document specifies only what APIIR constrains or adds.

### 2.1 Envelope constraints (APIIR-specific)

| Field | Constraint |
|---|---|
| `claim_type` | MUST be the exact string `"ar.redaction.v1"`. |
| `subject` | MUST be `null` (§4). APIIR is content-level; the content under redaction lives in the body as commits, never as the envelope subject. |
| `kind` | `observation` (default v1 issuers SHOULD emit). |
| `tsa` | OPTIONAL. No regulatory clock starts on a redaction pass; trusted timestamp is opt-in (FAMILY-CONSISTENCY §2). The TSA upgrade path is free — a `tsa` block may be added without changing `claim_type`. |
| `credentialStatus` | Absent. APIIR is a **Status-List non-consumer**: a redaction pass is a non-revocable event that *happened*; there is no suspension/revocation surface in v1 (FAMILY-CONSISTENCY §4). |
| `prev` | OPTIONAL. MAY chain a redaction receipt to a prior receipt in the same pipeline (e.g. a guard receipt) as additive bookkeeping, not required for validity. |

### 2.2 Leaf identity

`claimId = "ar.redaction.v1:" + envelope.id`. This claimId — not the bare `envelope.id` — is the single leaf preimage across the inline anchor, the audit-log key, and the daily Merkle root (`tree_head_root = "sha256:" + RFC6962-leafHash(claimId)`).

## 3. Body — `APIIRBody`

```jsonc
{
  "profile": "redaction.prompt",          // v1 ships one profile (§5)
  "counts": {                             // per-category removal counts
    "EMAIL": 2,
    "IBAN": 1,
    "VAT": 0,
    "PHONE": 3,
    "CARD": 0,
    "CLIENT": 4
  },
  "ruleset_hash": "sha256:<64hex>",       // golden-pinned detector rule corpus + version
  "input_commit":  "sha256:<64hex>",      // commit(salt, original_input)
  "output_commit": "sha256:<64hex>",      // commit(salt, sanitized_output_sent_to_model)
  "commit_alg": "sha256",
  "redactor": "@dekimuhq/ai@2.4.0"       // provenance string of which redactor produced counts
}
```

`field_root` (a `sha256:<hex>` selective-disclosure root over the committed fields) is added **issuer-side at mint** and appears in the receipt body; it is not part of the canonical body *input*.

### 3.1 Field rules

- **`profile`** — MUST be the literal string `"redaction.prompt"`. v1 is single-profile (§5).
- **`counts`** — a partial record over the fixed category set `{EMAIL, IBAN, VAT, PHONE, CARD, CLIENT}`. A category with zero removals MAY be omitted or set to `0`; the verifier and renderer treat absent keys as `0`. All present values MUST be non-negative integers. Unknown category keys are rejected.
- **`ruleset_hash`** — `sha256:<64hex>`. Golden-pins the exact detector rule corpus and version. Reproducibility anchor: a reader re-running the same pinned corpus over the same input SHOULD obtain the same counts. Same mechanism as `ar.guard.v1`'s `ruleset_hash`.
- **`input_commit`** — `sha256:<64hex>`. `commit(salt, original_input)` where `original_input` is the raw content before redaction. Never the content itself.
- **`output_commit`** — `sha256:<64hex>`. `commit(salt, sanitized_output)` where `sanitized_output` is the redacted text that actually left the process boundary toward the model — **not** the map-reversed output returned to the caller. This is the GDPR-relevant artifact.
- **`commit_alg`** — MUST be the literal string `"sha256"`. Version-lock for the commit primitive.
- **`redactor`** — non-empty string. Provenance of the redaction engine that produced `counts` (e.g. `"@dekimuhq/ai@2.4.0"`).

### 3.2 Commit discipline

Every commit is `sha256(salt_bytes ‖ value_utf8)` over a single UTF-8-encoded value, using the envelope's `commit(saltB64u, value)` primitive (`sha256:<hex>` output). A field binding two values MUST canonicalize them into one JSON object first (`commit(salt, canonicalize({...}))`) — never raw concatenation over variable-length operands.

## 4. Subject — null (content-level)

`subject` is `null` on every APIIR. The content under redaction is bound by body commits (`input_commit`, `output_commit`), never by the envelope subject. If a future profile genuinely targets a named data subject, that is a `v2` per-profile split, not a v1 change.

---

## 4.1 Commit-reveal and the salt/map boundary (security property)

The dual-commit design enables owner-side reveal without anchoring sensitive material:

- **Salt** is per-receipt cryptographically random, generated by the minting caller via the envelope's `randomSalt()` primitive. It is **never** in the receipt body, **never** anchored, **never** transmitted to any third party. It is the controller-only sensitive half.
- **Reversible redaction map** (placeholder → original PII value) is equally sensitive. It is **never** in the receipt, **never** anchored, never on `verify.dekimu.com`. The controller stores `{salt, map}` privately, scoped to the controller, never public.
- **What is publicly anchored:** only `counts`, `ruleset_hash`, `input_commit`, `output_commit`, `commit_alg`, and `redactor` — all non-sensitive.
- **Reveal:** to later prove that a specific sanitized prompt belongs to receipt X, the controller presents `(salt, text)` and any verifier recomputes `commit(salt, text)` against the stored `output_commit`. Identical mechanism to AActR's `request_id_commit`. Salt defends against dictionary attack when the input is a single short PII value (e.g. one email address as the entire content).

The commits bind **two** distinct artifacts under the **same** salt, so a controller reveal of `(salt, original)` re-derives `input_commit`, and a reveal of `(salt, sanitized)` re-derives `output_commit` — the two-sided nature is the audit trail: one receipt, two provable moments in the redaction pipeline.

## 5. Profiles (v1)

One profile: **`redaction.prompt`** — a prompt or content blob was redacted before being sent to a model. v1 is single-profile (YAGNI; mirrors AGR's single `guard.input`). The profile validator asserts:

- `profile` is exactly `"redaction.prompt"`.
- `counts` is an object; all keys are in `{EMAIL, IBAN, VAT, PHONE, CARD, CLIENT}`; all values are non-negative integers.
- `ruleset_hash`, `input_commit`, `output_commit` all match `sha256:[0-9a-f]{64}`.
- `commit_alg` is exactly `"sha256"`.
- `redactor` is a non-empty string.
- No unknown keys are present in the body.

Profile extensibility follows the family factory. A `redaction.document` or `redaction.structured` profile would be a v1 additive extension or a `v2` split depending on whether it changes subject rules.

## 6. Verification surface

- **Anchor log:** `https://verify.dekimu.com/redaction/v1` — RFC 9162 inclusion against the signed daily root.
- **Receipt verification:** signature + canonicalization + inclusion + body-shape + profile validator. The verifier confirms the receipt is well-formed and internally consistent.
- **Owner reveal:** the controller re-reveals `(salt, original_input)` or `(salt, sanitized_output)`, recomputes the corresponding commit, and confirms the receipt binds the exact content shown in their run-log.
- **What a single receipt does NOT prove.** A stateless single-receipt verifier confirms the receipt is well-formed and that the body fields are internally consistent (commit format, category set, profile literal). It CANNOT confirm that the redactor actually ran, that the reported counts are accurate, that no PII survived redaction, or that the content committed as `output_commit` is what the model received. Those are issuer-asserted and are not re-derivable from the signed bytes alone. `valid: true` here is never a PII-free guarantee — see §1.1.

---

## 7. Versioning

`ar.redaction.v1` is frozen on public flip. New fields are additive and OPTIONAL with graceful degradation; breaking changes require a `v2` discriminator. Adding a profile that requires a non-null `subject` is the canonical example of a `v2` split.

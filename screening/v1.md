## 1. What AScR is

An **AScR** (Anchored Screening Receipt) is a signed, machine-verifiable record that **a named party was screened against a named, hash-pinned sanctions list by a named, versioned matcher, and what the matcher returned** — anchored into a daily Merkle root and independently verifiable without trusting the issuer.

> **Honest claim:** AScR proves **which list file was checked, when, by which matcher, and with what result.** It never proves that the screened party is, or is not, subject to sanctions, that the issuer is compliant with any sanctions regime, or that a later screen would agree. The result vocabulary is `none_at_threshold | candidate`; the words "clear", "not sanctioned" and "compliant" are never used by the receipt, the renderer or any conformant integration.

AScR answers:

1. **Which list** — an id, the file name and date, the sha-256 of the file bytes exactly as served, a second sha-256 over the canonical parsed entries, the entry count and the time it was fetched.
2. **Which matcher** — package name, exact version and match threshold, pinned by the envelope `policy_hash`.
3. **Which party** — a salted commitment to the screened name. The name is never in the receipt.
4. **The result** — `none_at_threshold` or `candidate`, with the candidate references and scores.
5. **When** — `screened_at`, bounded against the list's `fetched_at` (§3.3).
6. **What triggered it** — `manual` or `scheduled`.

### 1.1 Demarcation from neighbouring families

| Family | Why it does not fit |
|---|---|
| AActR (`ar.action.v1`) | Records an *autonomous* action under an *owner-enabled rule* (§1). A user's "Check now" click, or a platform-wide cron, is neither. Its §4 routes "a decision about a named data subject" to a v2. |
| AGR (`ar.guard.v1`) | Screens untrusted *inbound content* against a ruleset, `subject` null (§4), and an **unsalted** `content_commit`: a short name could be brute-forced from the receipt. |
| ARR / ACR / ADR | Lifecycle of a data subject's consent, erasure or delegation. A screen is a point-in-time check, not a lifecycle. |
| **AScR (`ar.screening.v1`)** | **"Party P was screened against list file F by matcher M at time T and the result was R."** |

AScR is a new family rather than a profile of AActR or AGR so that its honesty boundary is stated in its own text and no frozen public spec is amended.

## 2. Wire format

An AScR is an **`ar.screening.v1` Claim** in the shared **v=2 envelope** (`@dekimuhq/anchors-envelope`): Ed25519-signed, RFC 8785 (JCS) canonical JSON, `claim_type`-discriminated. AScR adds **no cryptographic primitive**; it reuses the envelope core and the envelope `commit()` / `randomSalt()` verbatim. This document specifies only what AScR constrains or adds.

### 2.1 Envelope constraints

| Field | Constraint |
|---|---|
| `claim_type` | MUST be the exact string `"ar.screening.v1"`. |
| `subject` | MUST be `null` (§4). The screened party is bound by `subject_commit` in the body. |
| `kind` | MUST be `decision` (`screening.kind.not_decision`). |
| `prev` | MUST be `null` in v1. A chain of screens of one party would make the party linkable across receipts. A verifier MUST reject a non-null `prev` (`screening.prev.not_null`). |
| `tsa` | OPTIONAL (FAMILY-CONSISTENCY §2). |
| `credentialStatus` | Absent. AScR is a **Status-List non-consumer**: a screen is a non-revocable historical event (FAMILY-CONSISTENCY §4). |
| `policy_uri` / `policy_hash` / `policy_version` | Envelope-level OPTIONAL, but an AScR verifier MUST treat a missing or non-matching `policy_hash` as `screening.policy_hash.mismatch`. `policy_uri` MUST be null (the hash binds the matcher JSON, not a fetchable document). `policy_hash` = sha-256 of the JCS of `{ "package": matcher.name, "version": matcher.version, "threshold": matcher.threshold }` (§3.2). |

### 2.2 Leaf identity

`claimId = "ar.screening.v1:" + envelope.id`. This claimId is the single leaf preimage across the inline anchor, the audit-log key and the daily Merkle root.

## 3. Body — `AScRBody`

One profile: **`screening.list`**.

```jsonc
{
  "profile": "screening.list",

  // One id per screen. Never per party: records are overwritten per client,
  // so the screen id is the only handle on one specific screen.
  "screen_id": "01J…",                       // ULID

  "list": {
    "id":            "eu-fsf",               // stable list identifier
    "file_name":     "20261119-FULL-1_1.xml",
    "file_date":     "2026-11-19T00:00:00.000Z", // the file's own date (Last-Modified or header)
    "file_sha256":   "sha256:<64hex>",       // sha-256 of the bytes exactly as served
    "parsed_sha256": "sha256:<64hex>",       // sha-256 over the canonical parsed entries (§3.4)
    "entry_count":   5123,
    "fetched_at":    "2026-11-19T03:00:04.000Z"
  },

  "matcher": {
    "name":      "@dekimuhq/sanctions",      // read from the installed package, never hardcoded
    "version":   "0.2.0",
    "threshold": 0.85
  },

  // Salted commitment to the screened name. The salt is NOT in the receipt.
  "subject_commit": "sha256:<64hex>",        // commit(randomSalt(), trimmed query)

  "result": "none_at_threshold",             // "none_at_threshold" | "candidate"
  "candidates": [],                          // empty iff result = none_at_threshold
  "trigger": "manual",                       // "manual" | "scheduled"
  "screened_at": "2026-11-19T10:00:00.000Z"
}
```

A candidate entry:

```jsonc
{ "entry_ref": "EU.1234.56", "score": 0.91 }   // entry_ref = the list's own public entity id
```

### 3.1 Field rules

- `screen_id` — a valid ULID, unique per screen. An issuer MUST NOT reuse it. An idempotency key covers one screen, never one party.
- `list.id` — v1 defines exactly one value, `eu-fsf` (EU Financial Sanctions Files consolidated list); any other value is rejected (`screening.list.id_unknown`). New list ids are additive via a registry decision.
- `list.file_date` MUST NOT be later than `list.fetched_at`.
- Unknown keys anywhere in the body (top level, `list`, `matcher`, candidate entries) are rejected (`screening.body.unknown_field`), so plaintext party data cannot ride along. `field_root` is the one issuer-added key.
- `list.file_sha256` / `list.parsed_sha256` — `sha256:` followed by exactly 64 lowercase hex chars.
- `list.entry_count` — integer ≥ 1. An issuer MUST NOT mint a receipt from an empty list.
- `list.fetched_at`, `screened_at`, `list.file_date` — RFC 3339 UTC.
- `matcher.name` and `matcher.version` MUST be read from the installed matcher package at mint time. **This is an issuer obligation; the issuer kit takes the values from its caller and cannot check them.** `matcher.threshold` ∈ (0, 1].
- `subject_commit` — `sha256:<64hex>`, equal to `commit(salt, query)` from the envelope, where `query` is the trimmed screened string and `salt` is a fresh `randomSalt()` **per screen**. Salts MUST NOT be reused across screens, so one party's receipts are not linkable.
- `result` ∈ `{ "none_at_threshold", "candidate" }`. If `none_at_threshold`, `candidates` MUST be `[]`. If `candidate`, `candidates` MUST be non-empty, each `entry_ref` matching `^[A-Za-z0-9._:-]{1,64}$` (a list identifier, never free text), each `score` ≥ `matcher.threshold`, and entries ordered by descending score. At most 50 entries; a larger set records the top 50 and the issuer's own record keeps the rest.
- `trigger` ∈ `{ "manual", "scheduled" }`.
- Keys are absent, never `null`, when they do not apply.

### 3.2 Matcher identity

`policy_hash` binds `{package, version, threshold}`. A verifier that holds the same matcher version can reproduce it. Changing the matcher version or the threshold changes the hash, so receipts minted under different matchers are never conflated.

### 3.3 Freshness bound

For every AScR: `list.fetched_at ≤ screened_at ≤ list.fetched_at + 48h`. The reference verifier hard-fails a receipt outside the bound (`screening.list.stale`). The issuer MUST mint only from a screen that actually ran against a list satisfying the bound; an outage, a stale list or a failed refresh MUST NOT yield a receipt. The issuer MUST also refuse a list whose parsed entry count is implausible against the previous refresh (or has no previous count), and the kit refuses a `screened_at` more than 5 minutes after the mint time. A verifier rejects a receipt whose `screened_at` is more than 5 minutes after the envelope `iat` (`screening.screened_at.after_iat`). `screening.list.stale` measures the gap between list fetch and screen, not how old the list is today.

### 3.4 Reproducibility contract

`parsed_sha256` is the sha-256 of the JCS array of the list's canonical entries, sorted by entry id, as defined by the matcher package. The issuer SHOULD archive the raw file content-addressed under `file_sha256` for as long as it holds the receipt. Given the archived file, the matcher at `matcher.version`, the threshold and the reveal (§4), re-running the screen MUST produce the same `result` and `candidates`. The raw file is never carried in the receipt.

## 4. Subject — null, with a salted commitment

`subject` is `null` on every AScR. The screened party is bound only by `subject_commit`.

- The issuer retains the **reveal** (`salt` and the screened string) for the lifetime of the receipt, and exports it to the owner on request, so the owner can show which party a receipt covers by recomputing the commitment.
- The reveal is **personal data of the screened party**. It is covered by the issuer's erasure path. Erasing the reveal makes the receipt permanently non-attributable; the signed receipt itself carries no personal data and stays valid.
- A verifier without the reveal cannot recover the name from the commitment. With 256-bit per-screen salts the commitment is not brute-forceable.
- **Limit of this claim.** It holds for `none_at_threshold`. A `candidate` receipt carries entry references and scores computed by a public matcher over a public list, so a high score effectively identifies the party as the listed entity, and re-screens of one party against the same file produce the same candidate vector, which links those receipts. Issuers SHOULD NOT publish `candidate` receipts without the owner's decision.

AScR carries no party identifier other than this commitment. Entry references in `candidates` are public list identifiers, not data about the screened party.

## 5. Profiles (v1)

One profile: **`screening.list`**. The validator asserts everything in §3.1, plus: `profile === "screening.list"`, the freshness bound (§3.3), `candidates`/`result` coherence, and `policy_hash` ≠ absent.

**Authoritative vs advisory.** Signature validation, body well-formedness and the freshness bound are *authoritative*: a verifier MUST perform them. Re-running the matcher is *advisory*, because it needs the archived file and the reveal, which a verifier may not hold. The verifier records the issuer's asserted result and never re-runs the screen.

## 6. Verification surface

- **Anchor log:** `https://verify.dekimu.com/screening/v1`, RFC 9162 inclusion against the signed daily root.
- **Receipt verification:** signature + canonicalisation + inclusion + body shape + freshness bound + result coherence.
- **Error taxonomy** (the normative list is the reference validator, `@dekimuhq/screening-profiles` `validateScreeningList`, plus the verifier's own checks): body `body.not_object`, `screening.profile.unknown`, `screening.body.unknown_field`, `screening.screen_id.malformed`, `screening.subject_commit.malformed`, `screening.trigger.invalid`, `screening.screened_at_malformed`; list `screening.list.missing`, `.id_unknown`, `.file_name_missing`, `.file_date_malformed`, `.file_date_after_fetch`, `.fetched_at_malformed`, `.hash_malformed`, `.empty`, `.stale`; matcher `screening.matcher.missing`, `.threshold_invalid`; result `screening.result.invalid`, `.incoherent`, `screening.candidates.not_array`, `.too_many`, `.malformed`, `.below_threshold`, `.unordered`; envelope-level (verifier) `screening.policy_hash.mismatch`, `screening.prev.not_null`, `screening.kind.not_decision`, `screening.screened_at.after_iat`, and the envelope's own `subject_must_be_null`. Any failure sets `signature_valid` false in the reference verifier.
- **What a single receipt does NOT prove.** That the party is or is not sanctioned; that the list was complete or current at the issuer of the list; that other lists (UN, OFAC, UK) were checked; that a later screen would agree; that the screened party is the party the owner claims, without the reveal.

> **Required renderer text.** Every surface (this spec, `verify.dekimu.com`, integrations) MUST present: *"The issuer states that [party commitment] was screened against list file [name, date, hash] at [time] and the matcher returned [result]. This is not a determination of sanctions status. Later screens may differ."*

## 8. Versioning

`ar.screening.v1` is frozen on public flip. New fields are additive and OPTIONAL. Breaking changes require `v2`. Examples that require `v2`: a non-null `subject`; a non-null `prev`; carrying plaintext party data; changing the freshness bound; a non-deterministic matcher as a required field. New list ids and new result words are additive only via a registry decision.

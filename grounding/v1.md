## 1. What AGrR is

An **AGrR** (Anchored Grounding Receipt) is a signed, machine-verifiable record that the claims in a generated (typically RAG) answer were **bound to specific spans of named source documents**, with a reproducible binding-integrity check and a method-attributed support score — anchored into a daily Merkle root and independently verifiable without trusting the issuer.

AGrR answers:

1. **What answer was produced** — committed by `sha256`, never exposed in plaintext.
2. **What sources were cited** — each source hash-committed (`sha256` of the full document).
3. **Which claims were made** — each claim committed by `sha256`, never exposed.
4. **How each claim binds to its cited source** — per-citation span offsets + `span_commit` (`sha256(source[start:end])`), computed and verified by the grounding engine at mint time.
5. **What grounding score the named scorer produced** — a per-citation `score` ∈ [0,1] and `support` level (`supported` / `partial` / `unsupported`), under an identified scorer method, threshold, and version, recorded as advisory provenance of measurement.
6. **Coverage and grounded count** — the fraction of claims carrying ≥1 citation, and the count of claims with ≥1 `supported` citation, recomputed deterministically from the body by any verifier.

AGrR records **grounding provenance** — it proves that each cited claim points at a real, hash-committed span of the named source and that a named scorer produced a grounding score. It is **not** a guarantee that the answer is true, complete, or hallucination-free. The binding check is authoritative; the support score is advisory. See §1.2 and §6 for the precise demarcation.

### 1.1 Demarcation from neighbouring families

| Family | Answers |
|---|---|
| AER (`ar.evaluation.v1`) | "This AI system meets conformity / transparency obligations." |
| AQR (`ar.quality.v1`) | "An evaluator assessed output quality under this rubric." |
| AGR (`ar.guard.v1`) | "A screening pass checked *input* for prompt-injection / policy violations." |
| **AGrR (`ar.grounding.v1`)** | **"Every cited claim in this answer binds to a real, hash-committed source span; a named scorer assigned it a grounding score."** |

AGrR is RAG-output-specific: it asserts citation-binding and grounding-support provenance for generated answers. AER covers conformity attestation; AQR covers general rubric-based quality evaluation; AGR covers input screening. None of them answer the RAG-specific "do the cited claims actually resolve to the cited sources" question.

### 1.2 Honest claim — binding-authoritative, score-advisory

> **An AGrR proves grounding/citation provenance, not truth.** It proves that each cited claim binds to a real, hash-committed span of the named source, and records that a scorer produced a grounding score using the identified method. It does NOT certify that the answer is true, complete, or free of hallucinations. The citation-binding check is authoritative (deterministic and re-checkable by any holder of the sources); the support score is advisory (a measurement attributed to a named scorer method, version, and threshold — reproducible given the sources and the same scorer version, but not independently checkable by a stateless verifier).

This distinction is load-bearing. Any consumer of an AGrR receipt MUST communicate it to end users.

## 2. Wire format

An AGrR is an **`ar.grounding.v1` Claim** in the shared **v=2 envelope** (`@dekimuhq/anchors-envelope`): Ed25519-signed, RFC 8785 (JCS) canonical JSON, `claim_type`-discriminated. AGrR adds **no cryptographic primitive** — it reuses the envelope core verbatim. See [`envelope/`](../envelope/) for the shared wire mechanics; this document specifies only what AGrR constrains or adds.

### 2.1 Envelope constraints (AGrR-specific)

| Field | Constraint |
|---|---|
| `claim_type` | MUST be the exact string `"ar.grounding.v1"`. |
| `subject` | MUST be `null` (§4). The answer is not a data subject; citation targets live in the body as commits. |
| `kind` | `decision` (default v1.2 issuers SHOULD emit). |
| `tsa` | OPTIONAL. No regulatory clock starts on a grounding check; trusted timestamp is opt-in (FAMILY-CONSISTENCY §2). |
| `credentialStatus` | Absent. AGrR is a **Status-List non-consumer**: a grounding receipt is a non-revocable event record; there is no suspension/revocation surface in v1 (FAMILY-CONSISTENCY §4). |
| `prev` | OPTIONAL. v1 is single-receipt; `prev` MAY chain a grounding receipt to an originating receipt (e.g. an AActR for the RAG pipeline action) as additive bookkeeping, not required for validity. |
| `policy_uri` / `policy_hash` / `policy_version` | Envelope-level policy block is OPTIONAL. AGrR carries the reproducibility anchor — the scorer identity — inside the body; no external `policy_uri` is required. |

### 2.2 Leaf identity

`claimId = "ar.grounding.v1:" + envelope.id`. This claimId — not the bare `envelope.id` — is the single leaf preimage across the inline anchor, the audit-log key, and the daily Merkle root (`tree_head_root = "sha256:" + RFC6962-leafHash(claimId)`).

## 3. Body — `GroundingRagBody`

```jsonc
{
  "profile": "grounding.rag",              // v1 ships one profile (§5)
  "answer_commit": "sha256:<64hex>",       // sha-256 of the full answer text. Never the text itself.

  // Sources — each named source is hash-committed.
  "sources": [
    {
      "source_id": "doc-1#para-4",         // stable id referenced by citations. Non-PII.
      "source_commit": "sha256:<64hex>",   // sha-256 of the full source document.
      "media_type": "text/plain"           // OPTIONAL. e.g. "text/plain", "text/markdown"
    }
  ],

  // Claims — each claim in the answer is committed. The claim text never appears in the receipt.
  "claims": [
    {
      "claim_id": "c1",                    // stable id; referenced by citations.
      "claim_commit": "sha256:<64hex>"     // sha-256 of the claim text.
    }
  ],

  // Citations — zero or more; each binds a claim to a span of a named source.
  "citations": [
    {
      "claim_id": "c1",                    // MUST match a claims[].claim_id above.
      "source_id": "doc-1#para-4",         // MUST match a sources[].source_id above.
      "start": 120,                        // span start (JS UTF-16 code units, inclusive; §3.1).
      "end": 245,                          // span end (exclusive); end > start.
      "span_commit": "sha256:<64hex>",     // sha-256 of source[start:end]. The binding anchor.
      "support": "supported",              // "supported" | "partial" | "unsupported" (§3.2).
      "score": 0.82                        // 0..1 support score from the named scorer method.
    }
  ],

  // Derived fields — recomputed by any verifier from the body above. Mismatch ⇒ invalid.
  "coverage": 0.8,                         // |claims with ≥1 citation| / |claims| (§3.3).
  "grounded_count": 3,                     // # claims with ≥1 "supported" citation (§3.3).

  // Scorer identity — part of the reproducibility anchor.
  "scorer": {
    "method": "lexical_overlap",           // v1 locked; additive enum: "nli" | "llm_judge" in v2.
    "name": "dekimu/grounding-check",      // scorer implementation name.
    "version": "1.0.0",                    // scorer implementation semver.
    "threshold": 0.6                       // 0..1 — support-level cutoff; part of scorer identity (§3.2).
  },

  "scored_at": "2026-06-20T14:00:00.000Z", // RFC 3339 / ISO 8601 UTC — when scoring ran.
  "answer_media_type": "text/markdown",    // OPTIONAL — media type of the committed answer.

  // Mandate binding (§4.4 — OPTIONAL, additive).
  "credential_id": "<claimId>",            // authorizing mandate's credential id.
  "caveats_consumed": {                    // present iff credential_id is present.
    "data_scope": "ws_abc123",
    "spend_step": 1,
    "spend_currency": "api_call",          // OPTIONAL
    "capability": "grounding.check"
  }
}
```

`field_root` (a `sha256:<hex>` selective-disclosure root over committed fields) is added **issuer-side at mint** and appears in the receipt body; it is not part of the canonical body *input*.

### 3.1 Offset units

`start` and `end` are offsets in the reference grounding engine's native string indexing (JavaScript UTF-16 code units — `String.prototype.slice`). This is internally consistent and reproducible because the same engine resolves spans at both mint and verify; the signed `span_commit` hash is the authoritative binding anchor, not the raw offsets. Cross-language UTF-8 / Unicode-codepoint offset normalisation is a v2 interop concern — it changes only the offset *interpretation*, never the signed `span_commit`.

### 3.2 Support level and score — ordered mapping

The `support` field for each citation is deterministically derived from `score` and `scorer.threshold` by the following ordered mapping:

```
score === 0            ⇒  "unsupported"
score >= threshold     ⇒  "supported"
otherwise              ⇒  "partial"
```

This mapping resolves the `threshold === 0` and `threshold === 1` edges deterministically:

- `threshold === 0`: any non-zero overlap maps to `"supported"`; `"partial"` is unreachable.
- `threshold === 1`: only `score === 1` maps to `"supported"`; any positive score below 1 maps to `"partial"`.

The body's `support` value for each citation MUST equal the derived value for that citation's `score` and `scorer.threshold`. The verifier recomputes this without re-running the scorer (the formula is closed-form over the body fields alone). A mismatch is a hard validation error.

### 3.3 Derived fields — coverage and grounded_count

Both fields are **derived from the citation array**, not trusted from the issuer. The verifier recomputes them:

- **`coverage`** — `(# distinct `claim_id`s appearing in `citations`) / `claims.length``. A mismatch is a hard validation error.
- **`grounded_count`** — the number of claims having at least one citation with `support === "supported"`. A mismatch is a hard validation error.

### 3.4 Commitment discipline

Every `*_commit` field is `sha256(value_utf8)` over a single value (answer text, full source document text, claim text, or span text). The `span_commit` is `sha256(source[start:end])` — the span text in the reference engine's native indexing. Salts are NOT used for AGrR commits (the committed values are not PII — answer and source text are the pipeline's own output and inputs, not personal data). Issuers that handle potentially PII-adjacent content MAY apply salting at the application layer; the receipt body carries only the bare `sha256` hash.

## 4. Subject — null (answer-level)

`subject` is `null` on every AGrR. The answer and sources are not data subjects; their identities live as body commits (`answer_commit`, `sources[].source_commit`, `claims[].claim_commit`, `citations[].span_commit`), never as the envelope subject. If a future variant genuinely targets a named data subject, that is a `v2` per-profile split, not a v1 change.

### 4.4 Mandate binding (OPTIONAL, additive)

When a grounding check runs under a scoped agent credential (a capability mandate), the receipt MAY bind the authority it exercised:

- **`credential_id`** — the authorizing mandate's credential id. Plaintext and revocation-checkable. Absent for policy-authorized or unmanaged grounding checks.
- **`caveats_consumed`** — the attenuated authority this one grounding check spent: `data_scope` (the bound exercised, a non-PII selector), `spend_step` (budget units decremented), `spend_currency` (OPTIONAL unit label), `capability` (the capability invoked). These are plaintext, non-PII bounds — never the source or answer content.

**Binding integrity rules** (enforced by the reference verifier, §6):

- An empty `credential_id` is rejected.
- Malformed `caveats_consumed` is rejected.
- `caveats_consumed` present without `credential_id` is rejected (`caveats_consumed.orphan`).

Both fields are additive: receipts minted before this addition verify byte-equal, and unmanaged grounding checks simply omit them (keys absent, never `null`/`undefined`).

## 5. Profiles (v1)

One profile: **`grounding.rag`** — citation-binding + lexical grounding-support provenance for RAG answers.

The profile validator (`validateGroundingRag`) enforces all body rules from §3, including:

- `profile === "grounding.rag"`.
- `answer_commit` well-formed (64-char lowercase hex sha-256).
- `sources` non-empty; `source_id` unique; each `source_commit` well-formed.
- `claims` non-empty; `claim_id` unique; each `claim_commit` well-formed.
- `citations` array present (may be empty); each citation's `source_id` and `claim_id` must reference a declared source/claim (referential integrity); `start` and `end` non-negative integers with `end > start`; `span_commit` well-formed; `score` ∈ [0,1]; `support` ∈ `{supported, partial, unsupported}`.
- Per-citation support↔score coherence via the §3.2 ordered mapping (recomputed; mismatch ⇒ rejected).
- `coverage` and `grounded_count` recomputed from the citation array; mismatch ⇒ rejected.
- `scorer.method === "lexical_overlap"`; `scorer.name` and `scorer.version` non-empty; `scorer.threshold` ∈ [0,1].
- `scored_at` valid RFC 3339.

Profile extensibility follows the family factory. Future profiles (`grounding.summary`, `grounding.toolcall`) require separate specs and a v2 discriminator.

## 6. Verification surface

- **Anchor log:** `https://verify.dekimu.com/grounding/v1` — RFC 9162 inclusion against the signed daily root.
- **Receipt verification:** signature + canonicalization + inclusion + body-shape + internal-coherence checks (referential integrity, support↔score mapping, `coverage`, `grounded_count`).
- **Binding verify (authoritative, given sources):** a holder of the source documents re-resolves each citation's `[start, end]` span and confirms `span_commit === sha256(source[start:end])` and `source_commit === sha256(source)`. The reference issuer performs this verify-before-sign step at mint time; any party holding the sources may re-confirm independently.
- **Score verify (advisory, given sources and scorer):** a party holding the original answer + sources + the same scorer version may re-run `lexical_overlap` over each citation span and confirm the recorded `score`, `support`, `coverage`, and `grounded_count`. This requires the sources and the scorer — not possible for a stateless single-receipt verifier.

**What a stateless single-receipt verifier confirms.** A stateless verifier (including `verify.dekimu.com`) confirms the receipt is well-formed, internally coherent (referential integrity, derived-field arithmetic, support↔score boundary), and signed by a trusted issuer. It cannot re-resolve citation spans (it does not hold the sources) and cannot re-run the scorer. It can only confirm the body is internally consistent with the recorded scorer identity and threshold.

**What a stateless single-receipt verifier does NOT prove.** `valid: true` here confirms grounding provenance was recorded by a signing issuer — it is never a guarantee that the answer is true, complete, or free of hallucinations. Binding integrity (span existence) is issuer-asserted for a stateless verifier; score quality depends on the scorer method, its version, and whether the sources have since changed. These are verification surfaces for the issuing pipeline and any party holding the sources, not for a stateless receipt reader.

**What AGrR does NOT certify, ever.** An AGrR does not assert that the answer is factually correct, that all relevant information was retrieved, that the retrieval was unbiased, or that the model did not hallucinate content in uncited parts of the answer. It certifies that each cited claim was bound to a real source span at mint time, and records the scorer's measurement of lexical support for that binding. Read the §1.2 honest claim on every surface that displays or processes AGrR receipts.

## 7. Versioning

`ar.grounding.v1` is frozen on public flip. New fields are additive and OPTIONAL with graceful degradation; breaking changes require a `v2` discriminator. Examples of canonical v2 splits:

- Adding a new `scorer.method` value (`"nli"`, `"llm_judge"`) that breaks the closed-form support↔score derivation from the body alone.
- Changing the `subject` from `null` to a named data subject.
- Changing offset-unit semantics (e.g. UTF-8 byte offsets for cross-language reproducibility).

New additive OPTIONAL fields on the body, and new profiles with the same null-subject / non-revocable envelope constraints, are backward-compatible without a discriminator bump.

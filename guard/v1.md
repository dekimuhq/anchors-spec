## 1. What AGR is

An **AGR** (Anchored Guard Verdict) is a signed, machine-verifiable record that an **untrusted piece of inbound content was screened against a named, versioned, deterministic ruleset** — anchored into a daily Merkle root and independently verifiable without trusting the issuer.

> **Honest claim:** AGR proves **provenance of screening, not a guarantee of safety.** The receipt states "deterministic ruleset R (pinned by `ruleset_hash`) screened input/content X and returned verdict V at time T, signed by issuer I." It does **not** assert the content is safe. Detection is best-effort over known patterns; the verifier records the issuer's asserted verdict and never re-runs the detector. This mirrors the provenance-not-truth stance of AQR and is the reason AGR is an anchored primitive rather than just another guard SDK.

AGR answers:

1. **What was screened** — a content commitment (never the raw content, which may be untrusted/PII).
2. **By which ruleset** — `ruleset_id` + `ruleset_version` + `ruleset_hash` (a sha-256 over the deterministic corpus and decision policy, ensuring reproducibility).
3. **The verdict** — `pass`, `flagged`, or `blocked`, with per-match rule detail.
4. **When** — the screening timestamp.
5. **Under whose authority** *(optional)* — when screening ran under a scoped agent credential (a capability mandate), the receipt binds the authorizing `credential_id` and the slice of authority consumed.

### 1.1 Demarcation from neighbouring families

| Family | Answers |
|---|---|
| AER (`ar.evaluation.v1`) | "An AI model **evaluated** X and reached a conformity/quality judgement." |
| AQR (`ar.quality.v1`) | "An AI model **assessed output quality** — provenance of evaluation, not a truth verdict." |
| AActR (`ar.action.v1`) | "An agent **acted** — executed verb V against target D — on the workspace's behalf." |
| **AGR (`ar.guard.v1`)** | **"A deterministic ruleset **screened** inbound content and returned verdict V — provenance of screening, not a safety guarantee."** |

AGR is distinct from AER (conformity) and AQR (output quality). All three are provenance receipts, not truth assertions. AGR is the only family targeting *input-screening* and the only one that uses a fully deterministic, reproducible detection engine with no model involvement.

## 2. Wire format

An AGR is an **`ar.guard.v1` Claim** in the shared **v=2 envelope** (`@dekimuhq/anchors-envelope`): Ed25519-signed, RFC 8785 (JCS) canonical JSON, `claim_type`-discriminated. AGR adds **no cryptographic primitive** — it reuses the envelope core verbatim. See [`envelope/`](../envelope/) for the shared wire mechanics; this document specifies only what AGR constrains or adds.

### 2.1 Envelope constraints (AGR-specific)

| Field | Constraint |
|---|---|
| `claim_type` | MUST be the exact string `"ar.guard.v1"`. |
| `subject` | MUST be `null` (§4). The screened content is not a data subject; its identity lives in the body as `content_commit`. |
| `kind` | `decision` (default; v1 issuers SHOULD emit). |
| `tsa` | OPTIONAL. Trusted timestamp is opt-in (FAMILY-CONSISTENCY §2). |
| `credentialStatus` | Absent. AGR is a **Status-List non-consumer**: a screening verdict is a non-revocable historical event; there is no suspension/revocation surface in v1 (FAMILY-CONSISTENCY §4). |
| `prev` | OPTIONAL. MAY chain the screening verdict to a downstream action receipt or evaluation receipt as additive bookkeeping; not required for validity. |
| `policy_uri` / `policy_hash` / `policy_version` | OPTIONAL envelope-level policy block identifying the guard integration surface and the ruleset configuration under which screening ran. |

### 2.2 Leaf identity

`claimId = "ar.guard.v1:" + envelope.id`. This claimId — not the bare `envelope.id` — is the single leaf preimage across the inline anchor, the audit-log key, and the daily Merkle root (`tree_head_root = "sha256:" + RFC6962-leafHash(claimId)`).

## 3. Body — `AGRBody`

The v1 body has one profile: **`guard.input`** (deterministic input-screening verdict). All envelope-level fields (`issuer`, `subject`, `claim_type`, timestamps, `tsa`/`credentialStatus`/`policy` blocks) come from `@dekimuhq/anchors-envelope` and are NOT repeated in the body. `field_root` is added issuer-side by `mintGuardV1`.

```jsonc
{
  "profile": "guard.input",

  // Ruleset identity — the reproducibility anchor.
  "ruleset_id":      "dekimu/prompt-guard",       // stable name of the ruleset, e.g. "dekimu/prompt-guard"
  "ruleset_hash":    "sha256:<64hex>",            // sha-256 over ruleset corpus + decision policy (deterministic)
  "ruleset_version": "1.0.0",                     // semver of the ruleset

  // Content binding — commitment, never the content itself.
  "content_commit":  "sha256:<64hex>",            // sha-256 of the screened content bytes

  // Verdict.
  "decision": "pass",                             // "pass" | "flagged" | "blocked"
  "matched_rules": [],                            // empty on "pass"; non-empty on "flagged"/"blocked"

  // Detector metadata.
  "detector": {
    "engine":  "deterministic",                   // locked for v1; additive enum for future hybrid
    "name":    "dekimu/prompt-guard",             // detector implementation name
    "version": "1.0.0"                            // detector implementation semver
  },

  "screened_at": "2026-06-21T10:00:00.000Z",     // RFC 3339 UTC — when screening ran

  // Optional fields (omit when absent; never null/undefined).
  "content_media_type": "text/plain",             // OPTIONAL — MIME type of the screened content
  "credential_id":      "<claimId>",              // OPTIONAL — authorizing mandate claimId (§4.4)
  "caveats_consumed": {                           // OPTIONAL — present iff credential_id present
    "data_scope":     "ws_abc123",
    "spend_step":     1,
    "spend_currency": "EUR",                      // OPTIONAL sub-field
    "capability":     "guard.screen"
  }
}
```

A matched rule entry:

```jsonc
{
  "id":       "io.ignore-previous.v1",    // stable rule id
  "category": "instruction_override",     // see §3.1
  "severity": "critical"                  // "info" | "warn" | "critical"
}
```

### 3.1 Field rules

**Ruleset fields** (`ruleset_id`, `ruleset_hash`, `ruleset_version`):

- `ruleset_id` — non-empty string. Stable name of the detection ruleset; used alongside `ruleset_version` to identify the exact corpus.
- `ruleset_hash` — lowercase hex sha-256, exactly 64 chars. Computed deterministically over the canonicalized corpus: sorted rules (id, category, severity, pattern, flags) plus `ruleset_id`, `ruleset_version`, and `decision_policy`. **This is the reproducibility anchor**: a verifier or auditor who holds the same ruleset at the same version can independently reproduce the hash and confirm it matches.
- `ruleset_version` — non-empty semver-shaped string.

**Content commitment** (`content_commit`):

- Lowercase hex sha-256, exactly 64 chars, over the raw content bytes. The receipt commits to *what* was screened without carrying the (potentially untrusted, potentially PII-bearing) content itself. An owner who retains the original content can re-derive the commit and confirm the receipt is about it.

**Verdict fields** (`decision`, `matched_rules`):

- `decision` ∈ `{ "pass", "flagged", "blocked" }`.
- If `decision === "pass"` then `matched_rules` MUST be the empty array `[]`.
- If `decision !== "pass"` then `matched_rules` MUST be non-empty.
- Each entry in `matched_rules`: `id` non-empty string, `category` ∈ known enum (§3.2), `severity` ∈ `{ "info", "warn", "critical" }`.

**Decision policy** (baked into `ruleset_hash`):

The v1 policy maps severity to verdict escalation: `info → pass`, `warn → flagged`, `critical → blocked`. The overall `decision` is the maximum-rank verdict across all matched rules. The policy is part of the hashed corpus, so changing it produces a new `ruleset_hash`.

**Detector** (`detector`):

- `detector.engine` MUST be `"deterministic"` in v1 — the engine is locked to rule/regex predicates with no model involvement. The field is an additive enum: a future `"llm-judge"` hybrid would carry a different value and constitute a v2 profile.
- `detector.name` — non-empty string.
- `detector.version` — non-empty semver-shaped string.

**Timestamps** (`screened_at`): valid RFC 3339 datetime string.

**Optional fields** (`content_media_type`, `credential_id`, `caveats_consumed`): validated only when present; keys MUST be absent (never `null`) when the field does not apply.

### 3.2 Category taxonomy (v1)

Six categories form the v1 detection surface. The category list is part of the hashed corpus and can only grow via a new `ruleset_version`.

| Category | Covers |
|---|---|
| `instruction_override` | "Ignore previous instructions", role reassignment, disregard-system-prompt patterns |
| `system_prompt_leak` | Attempts to elicit, reveal, or print the system prompt |
| `delimiter_injection` | Fake role markers (`<\|system\|>`, `[/INST]`), end-of-prompt break-out |
| `encoding_obfuscation` | Base64 blobs, zero-width characters, homoglyphs, unicode tricks |
| `tool_hijack` | Tool/function-call coercion, exfiltration-to-URL phrasing |
| `jailbreak_template` | DAN-style prompts, "developer mode", known jailbreak templates |

### 3.3 Reproducibility contract

Given the original content bytes and the ruleset at `ruleset_version` (confirming `ruleset_hash` matches), re-running the detection engine MUST produce the identical `decision` and `matched_rules`. This is the verifiable core of AGR. The `content_commit` lets a verifier confirm the receipt is about a specific content blob without the body ever carrying the raw content.

## 4. Subject — null (content-level)

`subject` is `null` on every AGR. The screened content is not a data subject; its identity is bound by `content_commit` in the body. If a future profile genuinely targets a named data subject (e.g. a screening decision *about* a person), that is a `v2` per-event split, not a v1 change.

### 4.4 Mandate binding (OPTIONAL, additive)

When screening runs under a scoped agent credential (the capability door), the receipt MAY bind the authority exercised:

- **`credential_id`** — the authorizing mandate's claimId. Plaintext and revocation-checkable. Absent for policy-authorized screening that runs without a per-action mandate.
- **`caveats_consumed`** — the attenuated authority this one screening action spent: `data_scope` (the bound exercised, a non-PII selector), `spend_step` (budget units decremented), optional `spend_currency`, and `capability` (the guard capability invoked). Plaintext, non-PII *bounds* — never the screened data itself.

**Binding integrity rules** (enforced by the reference verifier, §6):

- An empty `credential_id` is rejected.
- Malformed `caveats_consumed` is rejected.
- `caveats_consumed` present without `credential_id` is rejected (`caveats_consumed.orphan`).

Both fields are additive: receipts minted before this addition verify byte-equal, and policy-authorized screenings simply omit them (keys absent, never `null`/`undefined`).

## 5. Profiles (v1)

One profile: **`guard.input`** — deterministic screening of inbound content before it reaches a model or automation. This is the only v1 profile. The profile validator asserts:

- `profile === "guard.input"`.
- `ruleset_hash` and `content_commit` are well-formed `sha256:<64hex>` strings.
- `ruleset_version` and `detector.version` are non-empty semver-shaped strings.
- `decision` ∈ `{ pass, flagged, blocked }`.
- `matched_rules` coherence: empty on `pass`, non-empty otherwise; each entry has a valid `id`, `category`, and `severity`.
- `detector.engine === "deterministic"`.
- `screened_at` is a valid RFC 3339 datetime.

Profile extensibility follows the family factory. A future `guard.output` profile (output/leakage screening) is out of scope for v1 and would require a separate spec.

**Authoritative vs advisory split** (mirror AQR spec §5): signature validation and body well-formedness are *authoritative* checks that a verifier MUST perform. Re-running the detection engine to confirm `decision` matches is *advisory* — it requires the original content, which the verifier may not hold, and the verifier is explicitly not a safety oracle.

## 6. Verification surface

- **Anchor log:** `https://verify.dekimu.com/guard/v1` — RFC 9162 inclusion against the signed daily root.
- **Receipt verification:** signature + canonicalization + inclusion + body-shape (profile, ruleset fields, content_commit, verdict coherence) + (when present) mandate-binding integrity.
- **Ruleset confirmation:** a verifier who holds the same `ruleset_id` at `ruleset_version` can independently compute `ruleset_hash` over the same deterministic corpus and confirm it matches the receipt. This is the reproducibility proof — independent of the issuer.
- **Content confirmation:** an owner who retains the original content can recompute `sha-256(content_bytes)` and confirm it equals `content_commit`, binding the receipt to the specific artifact screened.
- **What a single receipt does NOT prove.** A stateless single-receipt verifier confirms the receipt is well-formed, internally coherent, and (when present) that `credential_id` / `caveats_consumed` fields are *internally consistent*. It CANNOT confirm: that the content was actually safe; that the detection engine caught every possible attack pattern (v1 is known-pattern screening, not an exhaustive oracle); that a referenced mandate exists, is unrevoked, or actually granted the claimed scope. `valid: true` here is never a safety clearance — it is evidence that screening ran and the issuer signed the outcome.

> **Provenance, not safety.** Every surface — this spec, the renderer at `verify.dekimu.com`, and downstream integrations — MUST present this framing prominently. A guard verdict is evidence that screening ran against a named ruleset version; it is not a guarantee that the content is free of prompt-injection or any other attack.

---

## 7. Versioning

`ar.guard.v1` is frozen on public flip. New fields are additive and OPTIONAL with graceful degradation; keys MUST be absent (never `null`) when not applicable. Breaking changes require a `v2` discriminator. Canonical examples of changes that require `v2`:

- Adding a non-null subject (changing the must-be-null rule).
- Introducing a non-deterministic detection engine as a required field.
- Changing the `ruleset_hash` corpus definition in a non-additive way.

The ruleset corpus itself versioned separately via `ruleset_version`: each version increments semver, recomputes `ruleset_hash`, and old receipts remain reproducible against the version they cited.

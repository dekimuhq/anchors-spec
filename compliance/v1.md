## 1. What ACBR is

An **ACBR** (Anchored Compliance Bundle Receipt) is a signed, machine-verifiable record that **a controller's compliance evidence — its Art. 30 register (RoPA), any applicable DPIAs, and an obligation-satisfaction report — was assembled, referenced by content hash, and signed at a point in time** — anchored into a daily Merkle root and independently verifiable without trusting the issuer.

ACBR answers:

1. **Which controller** — the Art. 30(1)(a) identity (entity name, optional registered address and contact).
2. **Against which rulebook** — the regulation manifest (`gdpr`), its version and content hash.
3. **How much was covered** — the obligation counts (`applicable`, `satisfied`, `ratio`) the issuer's obligation engine reported.
4. **On what evidence** — references to the constituents: the RoPA register, the DPIA receipts (`ar.impact.v1`), and the obligation report, each bound by a `sha256:<hex>` content hash, with the obligation ids each one evidences.
5. **What is honestly missing** — a declared RoPA `gap` or a DPIA `not_applicable` determination, surfaced as such.
6. **When** — the assembly timestamp (`generated_at`).

### 1.1 Honest claim (load-bearing)

An ACBR evidences that **an assembly of referenced, independently re-verifiable artifacts was bound together and signed** at a point in time, with the coverage figures the issuer reported. It is **not** a regulator attestation of compliance and it does not certify that the controller complies with the GDPR.

The precise claim is:

> *Issuer I, for controller C, assembled at time T a bundle referencing RoPA register R (hash h_R), DPIA receipts D₁…Dₙ (hashes h_D), and obligation report O (hash h_O), against regulation manifest M (hash h_M), reporting coverage s/a, and signed it.*

ACBR **references; it never re-derives.** The receipt verifier checks the body's shape and the signature; it does not recompute obligation satisfaction, does not re-run a DPIA, and does not evaluate the register. A consumer who wants to trust the *content* of the bundle re-verifies each referenced constituent on its own terms (§6) — an ACBR is only as trustworthy as the receipts it points at. Declared absences (`gap`, `not_applicable`) are the controller owning up to what is missing; they are surfaced, never counted as satisfied evidence, and never fail verification by themselves.

The format is **designed to support** an accountability record under GDPR Art. 5(2), Art. 30, and Art. 35. Whether a given bundle satisfies a particular legal obligation is a question for the controller and the competent supervisory authority. This document is not legal advice.

### 1.2 Demarcation from neighbouring families

| Family | Answers |
|---|---|
| AIR (`ar.impact.v1`) | "A DPIA **was performed / reviewed / consulted on** — the Art. 35–36 lifecycle of one assessment." |
| APuR (`ar.purpose.v1`) | "A **purpose** was bound / repurposed / unbound (the Art. 30 register's per-activity purpose record)." |
| ASR (`ar.subject_rights.v1`) | "A **data-subject request** was handled." |
| **ACBR (`ar.compliance.v1`)** | **"At time T the controller's evidence set — register, DPIAs, obligation report — was assembled, hashed, and signed as one bundle with reported coverage s/a."** |

ACBR is the only family whose body is *about other receipts*. It is a workspace-level snapshot, not an event on any processing activity or data subject.

## 2. Wire format

An ACBR is an **`ar.compliance.v1` Claim** in the shared **v=2 envelope** (`@dekimuhq/anchors-envelope`): Ed25519-signed, RFC 8785 (JCS) canonical JSON, `claim_type`-discriminated. ACBR adds **no cryptographic primitive** — it reuses the envelope core verbatim. See [`envelope/`](../envelope/) for the shared wire mechanics; this document specifies only what ACBR constrains or adds.

### 2.1 Envelope constraints (ACBR-specific)

| Field | Constraint |
|---|---|
| `claim_type` | MUST be the exact string `"ar.compliance.v1"`. |
| `subject` | MUST be `null` (§4). A bundle is workspace-level; constituents reference data subjects by hash in their own receipts, never here. |
| `kind` | `observation` (default the reference issuer-kit emits when the caller passes none; the caller MAY set another v1.2 `kind` or `null`). |
| `cause` | OPTIONAL passthrough (`null` by default). |
| `predicate` | `null` as emitted by the reference issuer-kit (adoption Optional per [`registry.md`](../registry.md); not enforced by the verifier). |
| `tsa` | OPTIONAL. No regulatory clock starts on a compliance bundle; trusted timestamp is opt-in (upgrade path `free`, [family-consistency.md §2](../family-consistency.md)). |
| `credentialStatus` / `suspensionStatus` | Absent. ACBR is a **Status-List non-consumer**: a bundle is a point-in-time provenance snapshot — supersede with a newer receipt to reflect updated state, never revoke ([family-consistency.md §4](../family-consistency.md)). |
| `prev` | OPTIONAL. MAY chain a bundle to the previous bundle for the same workspace as additive bookkeeping; not required for validity and not walked by the reference verifier. |
| `policy_uri` / `policy_hash` / `policy_version` | `null` in v1 (the regulation manifest is bound in the body, §3). |
| `countersig` | `null` at mint; the daily anchor build MAY countersign as for every family. |

### 2.2 Leaf identity

`claimId = "ar.compliance.v1:" + envelope.id`. This claimId — not the bare `envelope.id` — is the single leaf preimage across the inline anchor, the audit-log key, and the daily Merkle root (`tree_head_root = "sha256:" + RFC6962-leafHash(claimId)`).

## 3. Body — `ComplianceBundleBody`

One profile (`compliance.bundle`, §5). The body is **plaintext by design**: a bundle is handed to a supervisory authority, who must be able to read it. No field is a salted commit; no field carries a data subject.

```jsonc
{
  "profile": "compliance.bundle",          // the single v1 profile (§5)
  "workspaceId": "ws_example",             // issuer-scoped workspace identifier (plaintext, non-PII)
  "controller": {                          // Art. 30(1)(a) identity, from the RoPA
    "entityName": "Example Controller",    // required, non-empty
    "registeredAddress": null,             // string | null
    "contactEmail": null                   // string | null
  },
  "regulation": {
    "manifestId": "gdpr",                  // v1 admits only "gdpr"
    "manifestVersion": "1.2.0",            // non-empty string
    "manifestHash": "sha256:<hex>"         // content hash of the compiled regulation manifest
  },
  "coverage": {
    "applicable": 8,                       // integer >= 0 — obligations the engine found applicable
    "satisfied": 8,                        // integer >= 0, <= applicable
    "ratio": 1                             // number in [0, 1] — issuer-reported, not recomputed (§3.1)
  },
  "constituents": {
    "ropa":        { /* BundleRef */ } | { "status": "gap", "reason": "…" },
    "dpia":        [ { /* BundleRef */ }, … ] | { "status": "not_applicable", "reason": "…", "basis": "…" },
    "obligations": { /* BundleRef — always present */ }
  },
  "generated_at": "2026-06-20T10:00:00Z"   // RFC 3339; the assembly clock
}
```

**`BundleRef`** — a reference to one constituent:

```jsonc
{
  "ref": "ropa:<registerHash>" | "<verify claim id>" | "report",   // non-empty; see §3.2 for per-role forms
  "contentHash": "sha256:<hex>",           // hash of the referenced artifact (canonical JSON, sha256)
  "claimType": "ar.impact.v1",             // OPTIONAL — the family of an anchored constituent
  "satisfiedObligations": ["gdpr.records"],// obligation ids this constituent evidences (may be empty)
  "embedded": { … }                        // OPTIONAL — the by-value payload that lets a verifier re-check
                                           //   this constituent without a round-trip (§3.3)
}
```

**Declarations** — honest absences, never evidence:

```jsonc
{ "status": "gap",            "reason": "RoPA not generated" }                                 // ropa only
{ "status": "not_applicable", "reason": "no high-risk processing", "basis": "engine:gdpr.dpia=not-applicable" }  // dpia only
```

`field_root` (a `sha256:<hex>` selective-disclosure root over the body) is added **issuer-side at mint** and appears in the receipt body; it is not part of the canonical body *input*.

### 3.1 Field rules (enforced by the reference body verifier)

- `profile` MUST equal `"compliance.bundle"` (`profile.invalid`).
- `workspaceId` non-empty string (`workspaceId.missing`).
- `controller.entityName` non-empty; `registeredAddress` and `contactEmail` each a non-empty string **or `null`** — never absent, never empty (`controller.invalid`).
- `regulation.manifestId` MUST be `"gdpr"`; `manifestVersion` non-empty; `manifestHash` MUST match `sha256:[0-9a-f]{64}` (`regulation.*`).
- `coverage.applicable` and `coverage.satisfied` non-negative integers; `coverage.ratio` a finite number in `[0, 1]`; `satisfied <= applicable` (`coverage.satisfied_exceeds_applicable`). **`ratio` is issuer-reported and is not recomputed** from `satisfied / applicable` by the verifier — like AQR's `verdict`, it is the issuer's asserted figure; a consumer MAY compare the two and treat a divergence as a trust signal.
- `constituents.ropa` is either a well-formed `BundleRef` or a `gap` declaration; `constituents.dpia` is either an array of well-formed `BundleRef`s (possibly empty — §6) or a `not_applicable` declaration; `constituents.obligations` MUST be a well-formed `BundleRef` (`constituents.*`).
- Every `BundleRef`: `ref` non-empty; `contentHash` matches `sha256:[0-9a-f]{64}`; `satisfiedObligations` an array of strings; `claimType`, when present, a non-empty string. `embedded` is not validated by the body verifier (it is opaque until a consumer re-checks it, §6).
- `generated_at` MUST be a parseable RFC 3339 timestamp (`generated_at.invalid`).

Error codes are dotted paths under the field that failed (e.g. `constituents.dpia[0].contentHash`); the body verifier returns every error it finds, and the issuer-kit refuses to sign on any (`verify-before-sign`).

### 3.2 Reference forms per role

| Role | `ref` form | `claimType` | `contentHash` is the hash of | `embedded` (when present) |
|---|---|---|---|---|
| `ropa` | `"ropa:" + <registerHash>` | absent | the canonical Art. 30 register | the controller's signed `ropa.register.v1` export (a by-value signed receipt the public verifier understands) |
| `dpia[i]` | the anchored DPIA receipt's verify claim id | `"ar.impact.v1"` | the cited receipt | normally absent — the receipt is fetched and re-verified by claim id |
| `obligations` | `"report"` (or an issuer-chosen id) | absent | the public obligation-coverage projection | that projection, so a verifier can recompute `contentHash` and confirm the coverage figures were not fabricated |

### 3.3 Self-containment

A bundle is designed to be independently checkable with **only the envelope, a family verifier, and the issuer's published keys** — no round-trip to the issuer's application. That is what `embedded` is for: the RoPA register is not anchored (it is a signed, by-value export), and an obligation report is not a receipt at all, so both are carried inside the bundle by value and bound by `contentHash`. DPIAs are already anchored `ar.impact.v1` receipts and are referenced by claim id instead.

### 3.4 RoPA composition note

This is where the Art. 30 register enters the Anchored Receipts family. ACBR does **not** define a RoPA wire format: the register is the controller's own artifact, exported as a separately signed `ropa.register.v1` receipt (a by-value signed object with its own `kind`, outside the `ar.*` namespace). ACBR binds that export by `contentHash` and, when `embedded`, carries it for re-verification. The bundle never re-derives the register, never asserts its completeness, and never evaluates the activities it records — a RoPA `gap` is declared, not inferred.

## 4. Subject — null (workspace-level)

`subject` is `null` on every ACBR. A bundle describes a controller's evidence set, not a data subject; the DPIA constituents reference subjects (where they do at all) inside their own receipts. If a future profile genuinely targets a named data subject, that is a `v2` split, not a v1 change.

## 5. Profiles (v1)

One profile: **`compliance.bundle`**. There are no per-profile validators; the family `body_schema` (§3.1) is the single, authoritative gate. Profile extensibility follows the family factory (a second profile would be a v1.x additive change with its own validator namespace).

## 6. Verification surface

- **Anchor log:** `https://verify.dekimu.com/compliance/v1` — RFC 9162 inclusion against the signed daily root.
- **Receipt verification (reference verifier):** envelope signature + canonicalisation + inclusion + body shape (§3.1). The reference verifier is **stateless and structural**: it never fetches, re-verifies, or re-derives a constituent.
- **Constituent re-verification (consumer-side; what the public verifier at verify.dekimu.com does on top):** a bundle's trust is gated on the receipts it references, so the public renderer re-checks every constituent that *claims* evidence and aggregates:

  | Constituent | Re-check | Outcome labels |
  |---|---|---|
  | `ropa` as `BundleRef` | re-verify `embedded` as a `ropa.register.v1` signed export against the public key catalogue (`verified` is the only passing status) | `valid_trusted` / `constituent_failed` |
  | `ropa` as `gap` | none | `declared_gap` (never a failure) |
  | `dpia[i]` | read the cited claim by id and re-verify its v=2 envelope; **gate on `trust_outcome === "valid_trusted"`** — a crypto-intact but untrusted DPIA fails | `valid_trusted` / `constituent_failed` |
  | `dpia` as `not_applicable` | none | `not_applicable` (never a failure) |
  | `dpia` as `[]` | none — nothing is evidenced; the wire cannot distinguish "none needed" from "needed but unevidenced", so the badge stays honest and `coverage` carries the completeness truth | `none_cited` (not a failure) |
  | `obligations` | recompute the canonical sha256 of `embedded` and compare to `contentHash` — integrity of binding only, not an independent trust anchor | `valid_trusted` / `constituent_failed` |

  **Aggregate:** `envelope_untrusted` whenever the bundle envelope's own `trust_outcome` is not `valid_trusted` (trusted parts inside an untrusted wrapper are not a trusted bundle); otherwise `constituent_failed` if any claimed constituent failed; otherwise `valid_trusted`. A missing `embedded` on a `ropa` or `obligations` `BundleRef` fails that constituent at the public verifier — the reference body verifier accepts it, the consumer-side gate does not.

- **What a single receipt does NOT prove.** A valid, trusted ACBR confirms that the issuer signed this assembly, that the body is well-formed, and (after the consumer-side re-check) that each cited constituent is itself intact and trusted. It CANNOT confirm that the register is complete or accurate, that the DPIAs reached correct conclusions, that `coverage` reflects the controller's real obligations, or that the controller is compliant with anything. `valid_trusted` is a provenance verdict over an evidence set, never a compliance verdict.

## 7. Versioning

`ar.compliance.v1` is frozen on public flip. New fields are additive and OPTIONAL with graceful degradation; breaking changes require a `v2` discriminator. A second `regulation.manifestId`, a revocable bundle surface (Status-List adoption), or a profile that changes the null-subject rule are canonical examples of `v2` or v1.x-additive decisions to be taken through governance, not slipped into v1.

## 8. Examples

[`examples/compliance-bundle.v1.json`](examples/compliance-bundle.v1.json) — a complete `ar.compliance.v1` envelope minted by the reference issuer-kit from the body shape of its own test suite (RoPA reference, DPIA `not_applicable`, obligation report with an `embedded` projection whose canonical hash equals its `contentHash`), then verified with the reference verifier (signature valid; the same envelope with `coverage.ratio` altered fails). The anchor block is a **mint-time placeholder** (`leaf_index 0`, empty `inclusion_proof`, all-zero `tree_head_root`): in production the daily anchor build attaches the real inclusion proof afterwards. The signing key is a fixed test seed and the issuer is `did:web:example.com` — **never add either to a trust anchor.** The RoPA reference carries no `embedded` export, so the public verifier would mark that constituent `constituent_failed` while the envelope itself verifies — a deliberate illustration of §6's two layers.

## 9. Changelog

### 1.0 — 2026-10-19 — first public spec

Written from the shipped reference implementation and its tests. Where the earlier internal design record and the shipped wire differ, **the code wins**; the differences:

- **`profile` and `generated_at` fields.** The design record's body had neither; the shipped body carries `profile: "compliance.bundle"` (required, the single profile discriminator) and `generated_at` (required RFC 3339 assembly timestamp, distinct from the envelope `iat`).
- **Envelope `kind`.** Not fixed by the design record; the issuer-kit defaults to `observation` (registered as such in [`registry.md`](../registry.md)).
- **`policy_*` fields** are `null` in v1 — the regulation manifest binding lives in `body.regulation`, not in the envelope policy block.
- **Coverage invariants** (`satisfied <= applicable`, `ratio ∈ [0, 1]`, non-negative integers) are enforced by the shipped body verifier; the design record listed the fields without constraints. `ratio` is issuer-reported, not recomputed.
- **Declarations are closed shapes.** The public verifier's parser rejects a `gap` / `not_applicable` object carrying extra keys, so a declaration can never smuggle an evidence-bearing `ref`; the reference body verifier accepts them by their `status` + required strings. Issuers MUST emit exactly the declared keys.
- **Public-verifier leniency.** The public renderer's parser is looser than the reference body verifier on `regulation.manifestHash` (any non-empty string) and `coverage` (any numbers); the reference verifier's rules (§3.1) are normative.
- **DPIA `[]`.** The design record did not address an empty DPIA array; the public verifier labels it `none_cited` (not a failure, not evidence).
- **Reference-implementation layout.** The design record planned `src/body.ts` / `src/verify.ts` / `src/mint.ts`; the shipped package exposes the body verifier, the family manifest, and a `./issue` issuer-kit — naming only, no wire effect.

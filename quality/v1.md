## 1. What AQR is

An **AQR** (Anchored Quality Receipt) is a signed, machine-verifiable record that **a defined evaluation suite was run against a specific output or software version, producing a scored result** — anchored into a daily Merkle root and independently verifiable without trusting the issuer.

AQR answers:

1. **What was evaluated** — the output or version gated, committed as a salted hash (never plaintext, because evaluated content may carry PII or proprietary detail).
2. **By which suite** — the suite identifier and its exact definition, pinned by a `suite_hash` so any third party can re-run and compare.
3. **How it was scored** — the scorer kind, model (when LLM-judge or hybrid), the numeric result, and the issuer's asserted verdict.
4. **When** — the timestamp the evaluation ran.
5. **Under whose authority** *(optional)* — when the evaluation itself ran under a scoped agent credential, the receipt may bind the authorizing `credential_id` and the authority consumed.

AQR records **evaluation provenance**, not quality truth. It does not assert the output is correct, safe, or good. The verifier records the issuer's asserted verdict; it never re-derives quality or rechecks the score against the suite. Trust in the *meaning* of a score derives from the suite being inspectable and reproducible — anyone can re-run the named suite against `suite_hash` — not from the issuer asserting quality.

This mirrors AActR's honesty: AActR proves *authority was consumed*, not that the action was wise; AQR proves *an evaluation happened as recorded and was not altered*, not that the verdict is ground truth.

> **Positioning phrase:** verifiable evaluation provenance, not verified truth. This is the only sound claim — "proving correctness" is not generally possible and must never be implied in copy, field names, or the verify renderer.

### 1.1 Demarcation from neighbouring families

| Family | Answers |
|---|---|
| AER (`ar.evaluation.v1`) | "This AI **system** passed its EU AI Act regulatory conformity assessment (Art.43) / carried its transparency disclosure (Art.50/52)." |
| AActR (`ar.action.v1`) | "An agent **acted** — executed verb V against target D — on the workspace's behalf." |
| **AQR (`ar.quality.v1`)** | **"Suite S (pinned by `suite_hash`) was run by scorer J and produced result R over output O at time T, signed by issuer I."** |

**AQR vs AER — must not be confused.** AER is an AI Act compliance family: its event types are `conformity` (Art.43) and `transparency` (Art.50/52), its scorers are notified bodies / provider self-assessments / NIST AI-RMF, and its claims are regulatory. AQR is an engineering quality family: its event is a golden-dataset / LLM-judge / human / deterministic suite score on a specific output or version. AQR never carries regulatory conformity claims (that is AER's job); AER never carries golden-suite quality scores (that is AQR's job). If a consumer requires both, they hold two receipts.

## 2. Wire format

An AQR is an **`ar.quality.v1` Claim** in the shared **v=2 envelope** (`@dekimuhq/anchors-envelope`): Ed25519-signed, RFC 8785 (JCS) canonical JSON, `claim_type`-discriminated. AQR adds **no cryptographic primitive** — it reuses the envelope core verbatim. See [`envelope/`](../envelope/) for the shared wire mechanics; this document specifies only what AQR constrains or adds.

### 2.1 Envelope constraints (AQR-specific)

| Field | Constraint |
|---|---|
| `claim_type` | MUST be the exact string `"ar.quality.v1"`. |
| `subject` | MUST be `null` (§4). AQR is suite/output-level; the evaluated artifact lives in the body as a commit (`output_commit`) or a plaintext version ref (`subject_ref`), never as the envelope subject. |
| `kind` | `decision` (default; v1 issuers SHOULD emit). |
| `tsa` | OPTIONAL. No regulatory clock starts on an engineering eval; trusted timestamp is opt-in (FAMILY-CONSISTENCY §2). |
| `credentialStatus` | Absent. AQR is a **Status-List non-consumer**: an evaluation is a non-revocable point-in-time fact — supersede with a newer eval receipt rather than revoke (FAMILY-CONSISTENCY §4). |
| `prev` | OPTIONAL. MAY chain an eval to an originating action receipt (e.g. an AActR for the agent run that produced the output) as additive bookkeeping, not required for validity. |
| `policy_uri` / `policy_hash` / `policy_version` | Envelope-level policy block identifying the eval config provenance and policy version under which thresholds were set. |

### 2.2 Leaf identity

`claimId = "ar.quality.v1:" + envelope.id`. This claimId — not the bare `envelope.id` — is the single leaf preimage across the inline anchor, the audit-log key, and the daily Merkle root (`tree_head_root = "sha256:" + RFC6962-leafHash(claimId)`).

## 3. Body — `AQRBody`

AQR uses two profiles, discriminated by `body.profile` (§5). The body below shows the common fields and each profile's additive fields.

**Common fields (both profiles):**

```jsonc
{
  "profile": "quality.output",               // "quality.output" | "quality.release" (§5)
  "suite_id": "operator.draft-reminder.golden.v3",  // plaintext, non-PII eval suite name
  "suite_hash": "sha256:<hex>",              // sha256:<hex> of canonical suite definition
  "scorer": {
    "kind": "llm-judge",                     // "deterministic"|"llm-judge"|"human"|"hybrid"
    "model": "claude-opus-4-8",              // REQUIRED when kind is "llm-judge" or "hybrid"
    "model_version": "20260101"              // OPTIONAL
  },
  "result": {
    "score": 0.92,                           // 0..1
    "verdict": "pass",                       // "pass"|"fail"|"warn" — issuer-asserted
    "threshold": 0.85,                       // 0..1
    "cases_total": 50,                       // integer >= 0
    "cases_passed": 46                       // integer, 0..cases_total
  },
  "ran_at": "2026-06-21T10:00:00.000Z",     // RFC 3339 / ISO 8601 UTC

  // Optional common fields
  "samples_commit": "sha256:<hex>",          // salted commit over eval inputs WHEN they carry PII
  "policy_uri": "https://...",               // eval/threshold config provenance
  "policy_hash": "sha256:<hex>",
  "policy_version": "v2"
}
```

**`quality.output` profile — additive fields:**

```jsonc
{
  // ... common fields above, with profile: "quality.output"

  "output_commit": "sha256:<hex>",           // REQUIRED — salted commit over the evaluated output
  "request_id_commit": "sha256:<hex>",       // OPTIONAL — links to originating agent run / AActR
  "credential_id": "<claimId>",             // OPTIONAL — authorizing mandate if eval was capability-gated
  "caveats_consumed": {                     // OPTIONAL — only valid WITH credential_id
    "data_scope": "ws_abc123",
    "spend_step": 1,
    "spend_currency": "eval_unit",          // OPTIONAL
    "capability": "quality.eval"
  }
}
```

**`quality.release` profile — additive fields:**

```jsonc
{
  // ... common fields above, with profile: "quality.release"

  "subject_ref": "agent-core@0.5.0",        // REQUIRED — plaintext software version (non-PII)
  "gate": "blocking"                         // "blocking"|"advisory" — whether eval gated the deploy
}
```

`field_root` (a `sha256:<hex>` selective-disclosure root over the committed fields) is added **issuer-side at mint** and appears in the receipt body; it is not part of the canonical body *input*.

### 3.1 Field rules

- **Plaintext fields** (`suite_id`, `scorer.kind`, `scorer.model`, `result.*`, `ran_at`, `subject_ref`, `gate`) are legible by design — a quality audit receipt is useless if the consumer cannot read what suite ran and how it scored. None is PII.
- **`suite_hash`** pins the exact suite definition (cases + scoring config) as a `sha256:<hex>` of the canonical suite content. This is the reproducibility anchor: a third party can re-run the named suite against this hash and compare results. A `suite_hash` mismatch means the score may have been produced by a different suite version.
- **`output_commit`** (`quality.output` only) is a salted `sha256` commit over the evaluated output, `commit(salt, canonicalize(output))`. Because evaluated content may carry PII (e.g. a generated email body with a debtor address), committing keeps the publicly-anchored, immutable receipt GDPR-clean while still binding the exact artifact. The salt lives in the issuer's reveal map, never in the signed envelope.
- **`samples_commit`** serves the same purpose for the evaluation inputs when they carry PII or proprietary client data. OPTIONAL; when the suite input is non-sensitive (e.g. a fixed golden dataset), it may be omitted.
- **`request_id_commit`** (`quality.output` only, OPTIONAL) links the eval receipt to an originating agent action run, enabling end-to-end traceability: AActR → AQR over the same run.
- **`verdict`** is **issuer-asserted**. The verifier records it; it does not recompute `score >= threshold`. Human-override verdicts (`warn` on marginal scores, `fail` on policy grounds regardless of score) are valid.
- **`result.cases_passed`** MUST be `0 ≤ cases_passed ≤ cases_total`. `cases_total: 0` is valid (some scorers aggregate continuously, not case-by-case).
- **`policy_uri` / `policy_version`** are unvalidated passthroughs — accepted as any string, not format-checked. Only `policy_hash` is format-validated.

### 3.2 Commit discipline

Every commit is `sha256(salt ‖ value_utf8)` over a single canonicalized value. A field binding two values MUST canonicalize them into one JSON object first (`commit(salt, canonicalize({...}))`) — never `H(a ‖ b)` over variable-length operands.

## 4. Subject — null (suite/output-level)

`subject` is `null` on every AQR. The evaluated artifact is a body commit (`output_commit`) or a plaintext version ref (`subject_ref`), never the envelope subject. An evaluation is a suite-level or version-level record, not a data-subject record. If a future profile genuinely targets a named data subject, that is a `v2` per-profile split, not a v1 change.

### 4.1 Mandate binding (OPTIONAL, additive — `quality.output` only)

When the evaluation itself ran under a scoped agent credential (e.g. the eval capability was gated behind the agent door), the receipt MAY bind the authority exercised:

- **`credential_id`** — the authorizing mandate's credential id (the ADR grant `claimId`). Plaintext. **Absent** when the eval ran under a policy-authorized automation rather than a per-action mandate.
- **`caveats_consumed`** — the attenuated authority this one eval spent: `data_scope`, `spend_step`, optional `spend_currency`, and `capability`. These are plaintext, non-PII bounds — the evaluated content stays in `output_commit`.

**Binding integrity rules** (enforced by the reference verifier, §6):
- `credential_id` present but empty: rejected.
- `caveats_consumed` present without `credential_id`: rejected (`caveats_consumed.orphan`) — caveats are meaningless without the credential they bound.
- `caveats_consumed` present but malformed: rejected.

Both fields are additive: receipts minted before this addition verify byte-equal, and policy-authorized evals simply omit them (keys absent, never `null`/`undefined`).

## 5. Profiles (v1)

Two profiles, discriminated by `body.profile`:

### `quality.output`

**When:** runtime, per-output evaluation — "Was this specific agent output evaluated, and how did it score?"

**Mandatory additional fields:** `output_commit`.

**Optional additional fields:** `request_id_commit`, `credential_id`, `caveats_consumed`.

**Profile validator asserts:** `profile === "quality.output"`; `suite_id` non-empty; `suite_hash` matches `sha256:<64hex>`; `scorer.kind` ∈ enum; `scorer.model` required when `kind ∈ {llm-judge, hybrid}`; `result.score` and `result.threshold` ∈ [0,1]; `result.verdict` ∈ enum; `result.cases_total` and `result.cases_passed` non-negative integers with `cases_passed ≤ cases_total`; `ran_at` non-empty RFC 3339 string; `output_commit` present and well-formed `sha256:<64hex>` (`quality.output.output_commit_missing` / `quality.output.output_commit_malformed`); `request_id_commit` well-formed when present; `caveats_consumed` only valid with `credential_id` (`quality.output.caveats_orphan` otherwise).

### `quality.release`

**When:** pre-deploy version gate — "Did this model/agent version pass its suite before deploy?"

**Mandatory additional fields:** `subject_ref`, `gate`.

**Profile validator asserts:** `profile === "quality.release"`; common suite/scorer/result/ran_at rules (same as `quality.output`); `subject_ref` non-empty string; `gate ∈ {blocking, advisory}`.

### Authoritative vs advisory split

The central `verifyQualityBody` function (the family `body_schema`) is the **authoritative** gate: it validates the full body including deep sub-shapes such as `caveats_consumed`. The per-profile validators (`validateQualityOutputProfile`, `validateQualityReleaseProfile`) are an **advisory** secondary surface, invoked only when a caller explicitly requests a profile check; they use a distinct error-code namespace (`quality.output.*`, `quality.release.*`) and do not re-validate every deep sub-shape the central verifier owns. The two never disagree on the central verdict — where a rule appears in both (e.g. the `ran_at` RFC 3339 check), it MUST be identical in both implementations. A `body_schema` pass is what a signature binds.

## 6. Verification surface

- **Anchor log:** `https://verify.dekimu.com/quality/v1` — RFC 9162 inclusion against the signed daily root.
- **Receipt verification:** signature + canonicalization + inclusion + body-shape + (when present) mandate-binding integrity (`credential_id` / `caveats_consumed` consistency).
- **Owner reveal:** the owner re-reveals the evaluated output (or the eval inputs) via the issuer's reveal map, re-derives `output_commit` / `samples_commit`, and confirms the receipt binds the artifact shown in their run-log.
- **Suite reproducibility:** any third party may re-run the suite named by `suite_id` against the version pinned by `suite_hash` and compare the resulting score with the recorded `result.score`. Divergence does not invalidate the receipt (it was correct at signing time) but informs trust in the suite's stability.
- **What a single receipt does NOT prove.** A stateless single-receipt verifier confirms the receipt is well-formed and that mandate-binding fields (when present) are internally consistent. It CANNOT confirm that the recorded score reflects any ground-truth quality, that the referenced mandate exists or was unrevoked, or that `verdict` was correctly derived from `score` and `threshold` — that last judgment is the issuer's asserted call and is intentionally not recomputed. `valid: true` is never a quality guarantee.

---

## 7. Versioning

`ar.quality.v1` is frozen on public flip. New fields are additive and OPTIONAL with graceful degradation; breaking changes require a `v2` discriminator. A profile that changes the null-subject rule (§4), adds a revocable evaluation surface, or changes the `cases_passed > cases_total` invariant are canonical examples of `v2` splits.

## 1. What AActR is

An **AActR** (Anchored Action Receipt) is a signed, machine-verifiable record that an **autonomous agent or automation engine executed an action on a workspace's behalf** — anchored into a daily Merkle root and independently verifiable without trusting the issuer.

AActR answers:

1. **What ran** — the dispatched verb, the owner-enabled rule, the catalog recipe, and the terminal outcome.
2. **When** — the execution timestamp.
3. **Against what target** — the decision, parameters, and idempotency key, bound as salted commits (never plaintext, because parameters may carry PII).
4. **Under whose authority** *(optional)* — when the action ran under a scoped agent credential (a capability mandate), the receipt binds the authorizing `credential_id` and the slice of authority that one action consumed.

AActR records an **effect on the world** (an email sent, a record drafted, a log entry written), keyed to the *decision* that authorized it and the *rule* under which the owner opted into automation. It is intentionally narrow: it does not assert the action was *correct*, that the agent told the truth at signing time, or that a referenced mandate actually granted the claimed scope (a stateless single-receipt verifier cannot check that — see §6).

### 1.1 Demarcation from neighbouring families

| Family | Answers |
|---|---|
| APR (`ar.provenance.v1`) | "An agent **produced** this artifact." |
| AER (`ar.evaluation.v1`) | "An agent **evaluated** X and reached verdict Y." |
| ADR (`ar.delegation.v1`) | "Authority was **delegated** under this scope." |
| **AActR (`ar.action.v1`)** | **"An agent *acted* — executed verb V against target D — on the workspace's behalf."** |

## 2. Wire format

An AActR is an **`ar.action.v1` Claim** in the shared **v=2 envelope** (`@dekimuhq/anchors-envelope`): Ed25519-signed, RFC 8785 (JCS) canonical JSON, `claim_type`-discriminated. AActR adds **no cryptographic primitive** — it reuses the envelope core verbatim. See [`envelope/`](../envelope/) for the shared wire mechanics; this document specifies only what AActR constrains or adds.

### 2.1 Envelope constraints (AActR-specific)

| Field | Constraint |
|---|---|
| `claim_type` | MUST be the exact string `"ar.action.v1"`. |
| `subject` | MUST be `null` (§4). AActR is workspace/activity-level; the action's target lives in the body as a commit, never as the envelope subject. |
| `kind` | `decision` (default v1.2 issuers SHOULD emit). |
| `tsa` | OPTIONAL. No regulatory clock starts on an autonomous action; trusted timestamp is opt-in (FAMILY-CONSISTENCY §2). |
| `credentialStatus` | Absent. AActR is a **Status-List non-consumer**: an action is a non-revocable event that *happened*; there is no suspension/revocation surface in v1 (FAMILY-CONSISTENCY §4). |
| `prev` | OPTIONAL. v1 is single-receipt; `prev` MAY chain an action to the decision's originating receipt (e.g. a Compass/APuR receipt) as additive bookkeeping, not required for validity. |
| `policy_uri` / `policy_hash` / `policy_version` | Envelope-level policy block identifying the automations surface and the recipe-catalog version under which the rule ran. |

### 2.2 Leaf identity

`claimId = "ar.action.v1:" + envelope.id`. This claimId — not the bare `envelope.id` — is the single leaf preimage across the inline anchor, the audit-log key, and the daily Merkle root (`tree_head_root = "sha256:" + RFC6962-leafHash(claimId)`).

## 3. Body — `AActRBody`

```jsonc
{
  "profile": "hub.automation",          // v1 ships one profile (§5)
  "verb": "invoiceup.remind",           // dispatched verb, <ns>.<op>. Plaintext, non-PII.
  "rule_id": "r1",                      // owner-enabled rule. Plaintext, non-PII.
  "recipe_id": "auto-remind-overdue",   // catalog recipe. Plaintext, non-PII.
  "outcome": "executed",                // "executed" | "failed-gave-up"
  "executed_at": "2026-06-07T10:00:00.000Z",  // RFC 3339 / ISO 8601 UTC

  // Target — committed, never exposed (params may carry PII).
  "decision_commit":   "sha256:<hex>",  // commit(salt, canonicalize(decisionId))
  "params_commit":     "sha256:<hex>",  // commit(salt, canonicalize(params))
  "request_id_commit": "sha256:<hex>",  // commit(salt, canonicalize(`${ruleId}:${decisionId}`)) — idempotency key

  // Mandate binding (§4.4 — OPTIONAL, additive).
  "credential_id": "<claimId>",         // authorizing mandate's credential id (= ADR grant claimId)
  "caveats_consumed": {                 // present iff credential_id is present
    "data_scope": "ws_abc123",          // the data-scope bound exercised (non-PII selector)
    "spend_step": 1,                    // budget units this action decremented
    "capability": "invoiceup.remind"    // the capability/verb invoked
  },

  // Delegation chain (§4.5 — OPTIONAL, additive). Present only when a SUB-agent acted
  // under an attenuated sub-mandate; root-only mandates omit it.
  "delegation_chain": {                 // present iff credential_id + caveats_consumed present
    "depth": 1,                         // delegation hops beyond root (integer >= 1)
    "leaf_key": "<base64url>",          // delegation key of the chain's leaf block
    "root_credential_id": "<claimId>"   // MUST equal credential_id
  }
}
```

`field_root` (a `sha256:<hex>` selective-disclosure root over the committed fields) is added **issuer-side at mint** and appears in the receipt body; it is not part of the canonical body *input*.

### 3.1 Field rules

- **Plaintext fields** (`verb`, `rule_id`, `recipe_id`, `outcome`, `executed_at`) are legible by design — an audit receipt is useless if the owner cannot read *what* the machine did. None is PII.
- **`decision_commit` / `params_commit` / `request_id_commit`** are salted `sha256` commits, `commit(salt, canonicalize(value))` over a **single** canonicalized value. Because `params` may carry low-entropy PII (e.g. a debtor email), committing keeps the publicly-anchored, immutable receipt GDPR-clean while still binding the exact target. Salts live in the issuer's owner-revealable reveal map, never in the signed envelope.
- **`request_id_commit`** binds the engine's idempotency key (`ruleId:decisionId`) so a receipt provably corresponds to exactly one logical action, not a retry storm.
- **`outcome: "failed-gave-up"`** also mints: "the machine tried and stopped" is as audit-worthy as a success.

### 3.2 Commit discipline

Every commit is `sha256(salt ‖ value_utf8)` over a single canonicalized value. A field binding two values MUST canonicalize them into one JSON object first (`commit(salt, canonicalize({...}))`) — never `H(a ‖ b)` over variable-length operands.

### 4. Subject — null (workspace-level)

`subject` is `null` on every AActR. The action's target is a body commit (`decision_commit` / `params_commit`), never the envelope subject. If a future verb genuinely targets a named data subject, that is a `v2` per-event split, not a v1 change.

### 4.4 Mandate binding (OPTIONAL, additive)

When an action runs under a scoped agent credential (the gated capability door), the receipt MAY bind the authority it exercised:

- **`credential_id`** — the authorizing mandate's credential id (the gateway `AgentCredentialEnvelope.credentialId`, equal to the ADR grant `claimId`). Plaintext and revocation-checkable. **Absent** for policy-authorized auto actions (an automation rule the owner enabled has no per-action mandate).
- **`caveats_consumed`** — the attenuated authority this one action spent: `data_scope` (the bound exercised, a non-PII selector), `spend_step` (budget units decremented), `capability` (the verb invoked). These are plaintext, non-PII *bounds* — never the data itself; any PII target stays in `params_commit`.

**Binding integrity rules** (enforced by the reference verifier, §6):
- An empty `credential_id` is rejected.
- Malformed `caveats_consumed` is rejected.
- `caveats_consumed` present without `credential_id` is rejected (`caveats_consumed.orphan`) — caveats are meaningless without the credential they bound.

Both fields are additive: receipts minted before this addition verify byte-equal, and policy-authorized actions simply omit them (keys absent, never `null`/`undefined`).

### 4.5 Delegation chain (OPTIONAL, additive)

When the authorizing mandate is a **delegation chain** — a sub-agent acting under an *attenuated sub-mandate* (Macaroons/biscuit-style narrowing), not the root principal's own mandate — the receipt MAY record the delegation path so a reader sees the action was taken by a sub-agent, not just the root credential:

- **`delegation_chain`** — `{ depth, leaf_key, root_credential_id }`:
  - **`depth`** — the number of delegation hops beyond the root mandate block. An integer `>= 1` (a root-only mandate — the principal's own agent acting directly — omits `delegation_chain` entirely; `depth 1` = the root delegated once to a sub-agent).
  - **`leaf_key`** — base64url delegation key of the chain's leaf block (the key the leaf delegate is authorized to hand onward). A stable identifier of the leaf's chain position, not the leaf's own signing identity.
  - **`root_credential_id`** — the root mandate's credential id. MUST equal `credential_id` (the root is the same credential whether or not it delegated onward).

**Binding integrity rules** (enforced by the reference verifier, §6):
- `delegation_chain` present without `credential_id` is rejected (`delegation_chain.orphan`).
- `delegation_chain` present without `caveats_consumed` is rejected (`delegation_chain.no_caveats`) — a delegated action that records its path but no consumed authority is incoherent.
- `root_credential_id !== credential_id` is rejected (`delegation_chain.root_mismatch`).
- `depth` that is not an integer `>= 1` is rejected.

**What `delegation_chain` does and does NOT prove.** Like `credential_id`, it is **issuer-asserted descriptive metadata**. The capability chain itself lives, signed, in the mandate token; recording its summary into the receipt introduces no new cryptographic primitive, and the security boundary (verify-time caveat-intersection over the actual token) is unchanged. A stateless single-receipt verifier — including `verify.dekimu.com` — sees only the receipt body and **cannot re-derive or cross-check** that the recorded chain actually existed; it can only confirm the body is internally consistent (the integrity rules above). Treat `delegation_chain` as "the issuer states this action ran at chain depth N," never as an independently verified delegation proof (§6).

Additive and backward-compatible: receipts minted before this addition verify byte-equal, and root-only / policy-authorized actions omit the field (key absent, never `null`/`undefined`).

## 5. Profiles (v1)

One profile: **`hub.automation`** — the Hub automations engine is the only v1 issuer. The profile validator asserts: `verb` matches the `<ns>.<op>` shape; `outcome ∈ {executed, failed-gave-up}`; `rule_id` / `recipe_id` non-empty; all three commits are well-formed `sha256:<64hex>`. Profile extensibility follows the family factory.

## 6. Verification surface

- **Anchor log:** `https://verify.dekimu.com/action/v1` — RFC 9162 inclusion against the signed daily root.
- **Receipt verification:** signature + canonicalization + inclusion + body-shape + (when present) mandate-binding integrity.
- **Owner reveal:** the owner re-reveals `decision` / `params` / `request_id` via the issuer's reveal map, re-derives the commits, and confirms the receipt binds the action shown in their run-log.
- **What a single receipt does NOT prove.** A stateless single-receipt verifier confirms the receipt is well-formed and (when present) that the `credential_id` / `caveats_consumed` / `delegation_chain` fields are *internally consistent*. It CANNOT confirm that the referenced mandate exists, is unrevoked, actually granted the claimed scope, or that the recorded delegation chain truly existed — those are issuer-asserted and stateful, checkable only by the issuing/consuming gateway (which runs mandate trust-bind, scope, revocation, replay, and caveat-intersection over the real capability token *before* minting). `valid: true` here is never proof that an action was authorized.

---

## 7. Versioning

`ar.action.v1` is frozen on public flip. New fields are additive and OPTIONAL with graceful degradation; breaking changes require a `v2` discriminator. A verb that targets a named data subject (changing the null-subject rule) is the canonical example of a `v2` split.

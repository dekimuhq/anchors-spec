## 1. What APR is

An **APR** (Agent Provenance Receipt) is a signed, machine-verifiable record that a given artifact was produced by a given agent, on behalf of a given principal, at a given time, with a stated disclosure level — anchored daily into a public Merkle root.

APR answers four questions about an artifact:

1. **What was produced** — content type and SHA-256.
2. **Who produced it** — agent kind (human / ai / template / hybrid), optional model + provider.
3. **Under whose authority** — principal identifier (or pseudonym, depending on disclosure tier).
4. **When and how anchored** — issuance timestamp and the daily Merkle root the receipt is bound to.

APR is intentionally narrow. It does not say *whether the artifact is correct*, *whether the agent told the truth at signing time*, or *whether the principal is who they claim to be*. See [`THREAT-MODEL.md`](./THREAT-MODEL.md).

## 2. Wire format

An APR is an **`ar.provenance.v1` Claim** as defined by the underlying claim format (Ed25519-signed, canonical-JSON), with an `APRBody` payload.

### 2.1 Claim envelope

```jsonc
{
  "v": 1,                       // claim envelope version
  "id": "<ULID>",               // 26-char Crockford ULID
  "kind": "ar.provenance.v1",             // fixed for APR v1
  "issuer": "<short string>",   // issuer identifier (e.g. "miniterms")
  "subject": "<string>",        // subject the receipt is about (free-form,
                                // typically the artifact id or a stable URL)
  "iat": 1715300000,            // unix seconds, non-negative integer
  "kid": "<key id>",            // public-key identifier, must resolve via verifier catalog
  "body": { ... APRBody ... },  // see §3
  "sig": "<base64url(64 bytes)>"// Ed25519 signature, see §4

  // Optional fields:
  "holder":   "<string>",       // optional holder identifier
  "audience": ["<string>"],     // optional audience list
  "exp":      1715900000,       // optional unix-seconds expiry
  "parent":   "<claimId>"       // optional parent claim id (chains)
}
```

**Required:** `v`, `id`, `kind`, `issuer`, `subject`, `iat`, `kid`, `body`, `sig`.
**Optional:** `holder`, `audience`, `exp`, `parent`.

`v` MUST be the integer literal `1` for this version.
`kind` MUST be the exact string `"ar.provenance.v1"`.

**Unknown top-level fields are not permitted.** A conforming verifier MUST reject any claim whose top-level object carries a key outside the required-plus-optional set listed above. Result: `tampered` / `schema_invalid` (§8 step 1). Future versions may introduce new optional fields under v1.x (§10), at which point the known-key set grows accordingly. Body-level extensibility is described in §3.

### 2.2 ULID (`id`)

Claim `id` MUST be a 26-character Crockford-Base32 ULID. ULIDs are time-prefixed and lexicographically sortable. APR v1 does not require time-ordering across issuers, but each issuer SHOULD use ULIDs to keep claim ids globally unique without coordination.

### 2.3 Identifiers

- `issuer`: short string (typically 1–32 chars), opaque to the verifier except that it MUST equal the `issuer` field on the resolved verifying key for `kid` (see §5.2). This binds a key to its issuer.
- `subject`: free-form string. Conventionally an artifact id (e.g. a ULID), a content hash, or a stable URL. APR v1 does not constrain its shape beyond being a string.
- `kid`: short string identifying the issuer's signing key. Verifiers resolve `kid → publicKey + issuer + optional notBefore/notAfter` via a catalog (see §5.2).

## 3. Body — `APRBody`

```jsonc
{
  "artifact": {
    "type": "commander.run.output" | "commander.run.codeChange" |
            "commander.run.email" | "commander.run.message" |
            "miniterms.document",
    "id": "<string>",
    "hash": "<hex sha256>",
    "hashAlgorithm": "sha256",        // fixed literal in v1
    "contentType": "<mime>",          // optional
    "sizeBytes": <non-negative int>   // optional
  },
  "agent": {
    "kind": "human" | "ai" | "template" | "hybrid",
    "model":     "<string>",          // optional, e.g. "claude-haiku-4-5-20251001"
    "provider":  "<string>",          // optional, e.g. "anthropic"
    "humanRole": "review" | "edit" | "draft" | "approve" | "none"  // optional
  },
  "authorization": {
    "principalId": "<string>"         // see §6 for pseudonymisation
  },
  "inputs": [                         // optional
    { "kind": "prompt" | "file" | "url" | "claim" | "schedule",
      "hash": "<string>",             // optional
      "source": "<string>",           // optional
      "claimId": "<string>" }         // optional, set when kind="claim"
  ],
  "startedAt":   <unix seconds, int ≥ 0>,
  "completedAt": <unix seconds, int ≥ 0>,
  "durationMs":  <int ≥ 0>,           // optional
  "disclosure": "public_minimal" | "public_full" | "metadata_only",
  "summary":    "<string>"            // optional, free-form short text
}
```

### 3.1 Required fields in body

`artifact`, `artifact.type`, `artifact.id`, `artifact.hash`, `artifact.hashAlgorithm`, `agent`, `agent.kind`, `authorization`, `authorization.principalId`, `startedAt`, `completedAt`, `disclosure`.

### 3.2 `artifact.type` enum

The v1 enum is intentionally small. It enumerates the surfaces actually issuing APRs at v1 freeze. v1.x MAY add new values (additive only — see §10). v2 MAY restructure the enum.

### 3.3 `artifact.hash`

Lower-case hexadecimal SHA-256 of the canonical bytes of the artifact, where canonical bytes are defined per `artifact.type` by the issuer's published canonicalisation policy. APR v1 does not standardise per-type canonicalisation; verifiers do not recompute artifact hashes — they verify that the signed `hash` is bound to the rest of the body.

### 3.4 `agent.kind`

- `human` — produced by a human, no automation in the loop.
- `ai` — produced by a model (LLM, generative model, etc.).
- `template` — produced by deterministic template substitution (no model).
- `hybrid` — model output meaningfully reviewed/edited/approved by a human; `humanRole` SHOULD be set.

### 3.5 `inputs[].kind`

- `prompt` — a prompt or instruction text.
- `file` — a file the agent consumed.
- `url` — a URL the agent fetched.
- `claim` — another APR or claim (`claimId` SHOULD be set).
- `schedule` — a cron / schedule trigger.

`hash` and `source` are optional; their semantics are issuer-defined.

## 4. Canonicalisation and signature

APRs are signed over the canonical JSON encoding of the **pre-signature object** — the full claim envelope with the `sig` field omitted.

### 4.1 Canonical JSON (RFC 8785-lite)

1. Object keys sorted by **UTF-16 code unit** (matches RFC 8785 and the JavaScript default sort).
2. **No whitespace** between tokens.
3. Numbers serialised via the shortest round-trippable decimal form (JavaScript `Number.prototype.toString`).
4. Strings are **UTF-8** with **NFC normalisation** applied to both keys and string values.
5. `NaN`, `+Infinity`, `-Infinity`, `undefined`, functions, symbols, and `bigint` MUST be rejected.
6. Circular references MUST be rejected.
7. Object members whose value is `undefined` MUST be omitted (not serialised as `null`).

A reference implementation is provided in [`apr-verifier`](https://github.com/dekimuhq/apr-verifier). v1 conformance is byte-equality on the published test vectors.

### 4.2 Pre-signature object

The pre-signature object is the claim with **all required and present optional fields except `sig`**, in the field set defined by §2.1, before canonicalisation.

### 4.3 Signing

The signing input is `UTF-8(canonicalize(preSig))`. The signature is computed with **Ed25519** (RFC 8032) using the issuer's private key for `kid`. The signature is encoded as **base64url without padding** (RFC 4648 §5).

### 4.4 Verifying

Verification is the symmetric operation: rebuild the pre-signature object, canonicalise, decode the base64url signature (which MUST decode to exactly 64 bytes), and verify against the public key resolved from `kid`. Any deviation is a hard failure.

## 5. Verification

### 5.1 Result shape

```ts
type VerifyResult =
  | { ok: true }
  | { ok: false; reason: VerifyFailureReason };

type VerifyFailureReason =
  | "schema_invalid"        // claim shape violated §2.1
  | "unknown_kid"           // kid not in catalog
  | "issuer_kid_mismatch"   // catalog issuer != claim.issuer
  | "kid_not_yet_valid"     // now < notBefore
  | "kid_no_longer_valid"   // now > notAfter
  | "expired"               // claim.exp set and now > exp
  | "signature_invalid";    // bad sig length or Ed25519 verify=false
```

Verifiers MUST return one of these. Conforming verifiers MUST NOT short-circuit a `signature_invalid` result based on heuristics (e.g. JSON shape lookalikes).

### 5.2 Key catalog

Verifiers resolve `kid` to a verifying key via a caller-supplied resolver of shape:

```ts
(kid: string) => VerifyingKey | undefined

interface VerifyingKey {
  kid: string;
  publicKey: Uint8Array;   // 32 bytes (Ed25519)
  issuer: string;          // MUST equal claim.issuer
  notBefore?: number;      // unix seconds
  notAfter?: number;       // unix seconds
}
```

A reference resolver that loads from a single `CLAIMS_VERIFY_KEYS_JSON` env (a `{ kid → entry }` JSON map) is provided in `apr-verifier`. Implementers MAY ship resolvers backed by `/.well-known/dekimu-claims-keys.json` fetches, an in-process map, or any other mechanism; the resolver contract is the only normative interface.

`publicKey` MUST be 32 bytes. `issuer` mismatch is `"issuer_kid_mismatch"`, not `"unknown_kid"`.

### 5.3 Time

Time checks (`exp`, `notBefore`, `notAfter`) use `Math.floor(Date.now() / 1000)`. Implementations SHOULD allow the caller to inject a clock for testability; the wire format does not specify clock skew tolerance in v1.

## 6. Disclosure tiers

Disclosure controls **what a verifier serves to a consumer of the receipt** — it does NOT change what was signed. The receipt's `body.disclosure` is signed; downgrading disclosure at serve time is allowed, upgrading is not.

### 6.1 `public_full`

The full body is served verbatim. Use only when every field is intentionally public.

### 6.2 `public_minimal`

The default public surface. The verifier serves:

- `artifact`: full (`type`, `id`, `hash`, `hashAlgorithm`, optional `contentType`, optional `sizeBytes`).
- `agent`: `kind`, optional `model`, optional `provider`, optional `humanRole`.
- `authorization`: ONLY `principalPseudonym = "u_" + first 8 hex chars of sha256(principalId)`. The raw `principalId` is NEVER served.
- `inputs`: only `{kind}` per input. `hash`, `source`, `claimId` are dropped.
- `startedAt`, `completedAt`, optional `durationMs`.
- `disclosure: "public_minimal"`.
- `redacted: true`.

`summary` is dropped.

### 6.3 `metadata_only`

The verifier serves only `{ disclosure: "metadata_only", redacted: true }`. The signature still verifies against the original (full) body, but no body fields are exposed.

### 6.4 Pseudonymisation

```
principalPseudonym = "u_" + first 8 hex chars of sha256_hex(principalId)
```

This is a non-reversible compression. Re-identification risk depends on the principal-id space; see [`PRIVACY-REVIEW.md`](./PRIVACY-REVIEW.md) for the v1 conclusion and residual-risk guidance.

## 7. Daily anchoring

Every APR is bound to a **daily anchor**: a Merkle root over all claim ids issued on a given UTC date, signed by a separate root-signing key.

### 7.1 Anchor date

The anchor date is the UTC `YYYY-MM-DD` derived from the claim's `iat` (unix seconds), unless the issuer has explicitly provided a different anchor date alongside the claim (issuers MAY pin a slightly later anchor date for end-of-day inclusion).

### 7.2 Daily root envelope

```jsonc
{
  "v": 1,
  "date": "YYYY-MM-DD",
  "rootHash": "<hex sha256>",
  "count": <int ≥ 0>,
  "kid": "<root key id>",
  "sig": "<base64url(64 bytes)>"
}
```

The signed payload is `canonicalize({ v: 1, date, rootHash })` (count + kid are envelope-level, NOT signed). The signature is Ed25519 over those canonical bytes, base64url-encoded.

### 7.3 Anchor verification states

| State | Meaning |
|---|---|
| **verified** | Daily root envelope's `sig` verifies under the resolved root `kid`, AND the claim's id is provably included in the published Merkle root for `date`. |
| **unanchored** | The daily root for `date` is not yet published. Receipts issued today are typically `unanchored` until the next day's root build. |
| **missing-from-anchor** | The daily root for `date` is published but the claim id is NOT included. This is a hard failure — either the receipt is fabricated or the issuer published it after the daily-root cutoff. |
| **root-sig-invalid** | The daily root envelope exists but its signature does not verify under any known root `kid`. |

The on-the-wire format of inclusion proofs (Merkle path encoding) is verifier-defined in v1. v1.x MAY standardise an inclusion-proof format. The normative invariant is: a verifier MUST reject any "verified" anchor state that does not actually prove inclusion.

### 7.4 Root keys vs claim keys

Root keys and claim keys are separate Ed25519 keypairs with separate catalogs. A given environment MAY use the same `kid` namespace, but the catalogs are independent.

## 8. Verification flow (normative)

A conforming verifier, given a serialised APR, an anchor envelope, a claim-key resolver, and a root-key resolver, MUST produce a result of the form:

```ts
{
  status: "verified" | "tampered" | "unverified",
  reasons: string[],
  // serving layer (optional, separable):
  body?: DisclosedAprBody
}
```

with the following decision rules:

1. Parse the claim envelope and check shape (§2.1). If the shape is invalid → `tampered`, reason `"schema_invalid"`.
2. Resolve `kid` and run signature verification (§4, §5). On failure → `tampered` with the corresponding reason. On `unknown_kid` → `tampered` (a missing key is indistinguishable from a forged claim from the verifier's perspective; the spec deliberately treats it as tamper rather than as transient).
3. Verify the daily root envelope's signature. On failure → `unverified`, reason `"root-sig-invalid"`.
4. Check anchor state:
   - `verified` → `verified`.
   - `unanchored` → `verified` if claim is dated today, else `unverified` reason `"unanchored"`.
   - `missing-from-anchor` → `tampered`, reason `"missing-from-anchor"`.
5. Apply disclosure (§6) to produce the served body.

`status` is a closed three-value enum in v1. New reasons MAY be added in v1.x; new status values MAY NOT.

## 9. Test vectors

Conformance test vectors live in [`conformance/test-vectors/`](./conformance/) and cover:

- A valid signed claim with a `verified` anchor.
- The same claim with one mutated body field (→ `tampered` / `signature_invalid`).
- A claim whose id is missing from a published daily root (→ `tampered` / `missing-from-anchor`).
- A claim whose `kid` was rotated: an older `kid` whose key is still in the catalog still verifies.
- A claim whose `kid` is not in the catalog (→ `tampered` / `unknown_kid`).

Vectors are deterministic and run with no network access. A conforming `apr-verifier` MUST reach the documented status + reasons on every vector.

## 10. Versioning policy

- **v1 is frozen on the day this repo flips public.** No breaking changes will land in v1.
- **v1.x is additive only.** Allowed additive changes: new optional fields on `APRBody`, new values on closed-enum sets only when the verifier behaviour for unknown values is explicitly specified, new optional inputs metadata, new conformance vectors, new verification reasons (existing reason strings are stable).
- **v2** is required for any change that breaks byte-equality of the canonicalisation, changes the signature scheme, removes fields, narrows enums, restructures `APRBody`, or alters the disclosure-tier semantics.
- See [`CHANGELOG.md`](./CHANGELOG.md) for SemVer + LTS policy and full change history.
